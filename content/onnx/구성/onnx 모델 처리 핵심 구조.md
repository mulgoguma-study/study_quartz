Go에서 ONNX 모델을 처리할 때 핵심 구조는 거의 고정적입니다.

**일반적인 구조:**

```
1. Pool/Manager (리소스 관리)
   ↓
2. Session (모델 인스턴스)
   ↓
3. Buffer/Tensor (입출력 데이터)
   ↓
4. Processor/Executor (실행 엔진)
   ↓
5. Engine/Runtime (저수준 실행)
```

**변하지 않는 이유:**

1. **ONNX Runtime API 구조**: C API 자체가 이런 패턴을 강제합니다
    
    - Session 생성/관리
    - Tensor 할당/변환
    - Run 실행
2. **메모리 안전성**: Go의 GC와 C의 수동 메모리 관리 경계를 명확히 해야 합니다
    
3. **동시성 처리**: 여러 고루틴에서 안전하게 사용하려면 Pool 패턴이 필수입니다
    
4. **성능 최적화**: Buffer 재사용, Session 풀링 등은 표준 패턴입니다
    

**모델마다 달라지는 부분:**

- 입출력 텐서의 shape/dtype
- 전처리/후처리 로직
- 도메인별 비즈니스 로직

하지만 **핵심 인프라 코드는 거의 동일**하게 유지되므로, 한 번 잘 만들어두면 다양한 ONNX 모델에 재사용할 수 있습니다.
