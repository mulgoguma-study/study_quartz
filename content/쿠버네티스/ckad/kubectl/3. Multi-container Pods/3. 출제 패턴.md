Multi-container Pod은 다음 5가지 유형으로 정형화되어 있습니다.

#### 패턴 1: Sidecar로 로그 수집 (가장 자주 출제)

"메인 컨테이너의 로그를 별도 컨테이너에서 tail하라."

핵심 포인트:

- emptyDir로 로그 디렉토리 공유
- 메인은 그 디렉토리에 로그 쓰기
- Sidecar는 그 디렉토리를 mount하고 `tail -f`

```yaml
spec:
  containers:
  - name: app
    image: busybox
    command: ["sh", "-c", "while true; do echo $(date) >> /var/log/app.log; sleep 5; done"]
    volumeMounts:
    - name: logs
      mountPath: /var/log
  - name: sidecar
    image: busybox
    command: ["sh", "-c", "tail -f /logs/app.log"]
    volumeMounts:
    - name: logs
      mountPath: /logs
  volumes:
  - name: logs
    emptyDir: {}
```

검증: `k logs my-pod -c sidecar`로 sidecar가 메인의 로그를 받고 있는지 확인.

#### 패턴 2: Init container로 서비스 대기

"메인 컨테이너 시작 전에 특정 Service가 준비될 때까지 기다리게 하라."


```yaml
spec:
  initContainers:
  - name: wait-for-svc
    image: busybox
    command: ["sh", "-c", "until nslookup my-svc; do echo waiting; sleep 2; done"]
  containers:
  - name: app
    image: nginx
```

**검증 흐름**:

1. Service가 없는 상태에서 Pod 생성 → Pod이 `Init:0/1`에 머무름
2. Service를 생성하면 init이 성공 → 메인 컨테이너 시작 → `Running`

#### 패턴 3: Init container로 파일/설정 준비

"메인이 시작되기 전에 init container가 설정 파일을 만들어 두게 하라."


```yaml
spec:
  initContainers:
  - name: prepare
    image: busybox
    command: ["sh", "-c", "echo 'config-data' > /work/config.txt"]
    volumeMounts:
    - name: workdir
      mountPath: /work
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: workdir
      mountPath: /usr/share/nginx/html
  volumes:
  - name: workdir
    emptyDir: {}
```

#### 패턴 4: 두 컨테이너 간 볼륨 공유

"두 컨테이너가 같은 emptyDir을 마운트해서 한쪽은 쓰고 한쪽은 읽게 하라."


```yaml
spec:
  containers:
  - name: writer
    image: busybox
    command: ["sh", "-c", "while true; do date > /shared/time.txt; sleep 5; done"]
    volumeMounts:
    - name: data
      mountPath: /shared
  - name: reader
    image: busybox
    command: ["sh", "-c", "while true; do cat /shared/time.txt; sleep 5; done"]
    volumeMounts:
    - name: data
      mountPath: /shared
  volumes:
  - name: data
    emptyDir: {}
```

검증: `k logs my-pod -c reader`로 reader가 writer의 출력을 읽는지 확인.

#### 패턴 5: 디버깅 — 어느 컨테이너가 문제인가

"Multi-container Pod이 정상 동작하지 않는다. 원인을 찾아라."


```bash
k get pod my-pod                       # READY 컬럼 확인 (예: 1/2 → 컨테이너 중 하나 다운)
k describe pod my-pod                  # 어느 컨테이너에서 어떤 에러
k logs my-pod -c sidecar               # 각 컨테이너 로그
k logs my-pod -c sidecar --previous    # 재시작 전 로그
k exec -it my-pod -c sidecar -- sh     # 직접 접속해서 확인
```

### 함정 포인트

#### 함정 1 — containers vs initContainers 위치

```yaml
spec:
  initContainers:    # ✅ init은 여기
  - name: init
    ...
  containers:        # ✅ 메인 컨테이너는 여기
  - name: main
    ...
```

Init container를 `containers` 배열에 넣으면 그냥 일반 컨테이너로 취급되어 의도한 순차 실행이 안 됩니다.

#### 함정 2 — volumeMounts의 name 불일치


```yaml
containers:
- volumeMounts:
  - name: data       # 이거와
    mountPath: /data
volumes:
- name: datavol      # 다르면 Pod 생성 실패
  emptyDir: {}
```

특히 두 컨테이너가 같은 볼륨을 mount할 때, **양쪽 모두 같은 volume name**을 써야 합니다. mountPath는 달라도 됩니다.

#### 함정 3 — mountPath는 같지 않아도 됨


```yaml
containers:
- name: writer
  volumeMounts:
  - name: shared
    mountPath: /var/log     # writer는 /var/log에 마운트
- name: reader
  volumeMounts:
  - name: shared
    mountPath: /logs        # reader는 /logs에 마운트
```

같은 볼륨을 서로 다른 경로에 마운트할 수 있습니다. 시험 문제에서 헷갈리지 마세요.

#### 함정 4 — 포트 충돌

같은 Pod 안의 컨테이너끼리 **같은 포트를 listen할 수 없습니다**. 둘 다 nginx를 80 포트로 띄우면 두 번째 컨테이너가 크래시.

#### 함정 5 — Init container의 restartPolicy

Init container는 Pod 레벨 `restartPolicy`에 따라 재시도됩니다.

- `Always` (기본): 실패 시 무한 재시도
- `OnFailure`: 실패 시 재시도
- `Never`: 한 번 실패 시 Pod 전체 Failed

Job에서 init container를 쓰면 `restartPolicy`가 `Never`/`OnFailure`이므로 주의.

#### 함정 6 — `k logs`에서 컨테이너 이름 누락


```bash
k logs my-pod        # ❌ multi-container면 에러
k logs my-pod -c web # ✅
```

에러 메시지에 가능한 컨테이너 이름이 나오니 그걸 보고 다시 시도하면 됨.

#### 함정 7 — Init container도 `command`/`args` 적용

Init container도 일반 컨테이너와 동일하게 `command`/`args` 사용. ENTRYPOINT를 덮어쓰는 것이고, 이미지 자체의 명령을 그대로 쓰려면 `command`를 지정하지 않으면 됩니다.

#### 함정 8 — Pod 상태로 init 진행 확인

```bash
k get pod my-pod
# NAME      READY   STATUS     RESTARTS   AGE
# my-pod    0/1     Init:0/2   0          10s    ← init 0개 완료, 총 2개

# 완료되면
# my-pod    1/1     Running    0          1m
```

`Init:0/2`는 정상 진행 중. `Init:Error`나 `Init:CrashLoopBackOff`면 init이 실패한 상태.

#### 함정 9 — Sidecar가 먼저 죽으면 메인은?

기본 동작: 사이드카가 죽고 다시 살아나도 메인은 그대로. 하지만 사이드카가 계속 크래시하면 Pod의 `READY`가 `1/2`로 떨어지고 Service의 endpoint에서 제거될 수 있음.

#### 함정 10 — 같은 컨테이너 이름 사용 불가

yaml

```yaml
containers:
- name: app          # ❌
  image: nginx
- name: app          # ❌ 같은 이름
  image: busybox
```

Pod 안에서 컨테이너 이름은 unique해야 합니다.

### 디버깅 명령

```bash
# 상태 확인
k get pod my-pod
k get pod my-pod -o wide
k describe pod my-pod                  # 가장 유용. Init 진행, 컨테이너 상태, 이벤트 모두

# 컨테이너별 로그
k logs my-pod -c <container>
k logs my-pod -c <container> --previous
k logs my-pod --all-containers

# 컨테이너 접속
k exec -it my-pod -c <container> -- sh

# Init 진행 확인
k get pod my-pod -w                    # watch 모드로 상태 변화 추적

# 컨테이너 이름 목록 확인
k get pod my-pod -o jsonpath='{.spec.containers[*].name}'
k get pod my-pod -o jsonpath='{.spec.initContainers[*].name}'

# Volume mount 확인
k get pod my-pod -o yaml | grep -A 5 volumeMounts
```

### 빠르게 작성하는 팁

- **첫 컨테이너는 `k run`으로 골격 생성**, 두 번째부터 YAML에 손으로 추가. 처음부터 YAML 쓰지 말 것.
- **자주 쓰는 명령 한 줄 외워두기**:

```yaml
  command: ["sh", "-c", "while true; do echo hello; sleep 5; done"]
  command: ["sh", "-c", "tail -f /logs/app.log"]
  command: ["sh", "-c", "until nslookup my-svc; do sleep 2; done"]
```

- **`emptyDir`이 multi-container 문제의 90%**. 두 컨테이너가 데이터를 공유한다면 거의 무조건 emptyDir.
- **검증은 항상 logs로**:


```bash
  k logs my-pod -c sidecar -f
```

Pod이 Running이라도 sidecar가 의도대로 동작하는지 logs로 확인 필수.

- **Init container 디버깅은 `describe`가 최고**. `kubectl describe pod`의 Init Containers 섹션이 진행 상황을 가장 명확히 보여줌.
- **`-c` 옵션 습관화**: multi-container Pod에서는 logs, exec 모두 `-c <컨테이너이름>`. 안 붙이면 에러.
- **포트가 다른지 확인**: 두 컨테이너가 모두 listen한다면 포트가 안 겹치는지 체크.
