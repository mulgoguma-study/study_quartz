# Configuration



## 1. Configuration의 핵심 주제

크게 6가지로 나뉩니다.

- **ConfigMap**: 일반 설정 데이터
- **Secret**: 민감한 데이터 (base64 인코딩)
- **Resource Requirements**: CPU/Memory requests, limits
- **SecurityContext**: Pod/Container 보안 설정
- **ServiceAccount**: Pod의 API 접근 신원
- **Env / Args / Command**: 컨테이너 동작 제어

## 2. ConfigMap

애플리케이션 설정값을 Pod와 분리해서 관리합니다.

### 생성 방법 (4가지)

```bash
# 1. literal로 직접
k create cm app-config --from-literal=ENV=prod --from-literal=LOG_LEVEL=debug

# 2. 파일에서 (파일명이 key, 내용이 value)
k create cm app-config --from-file=app.properties
k create cm app-config --from-file=config1.txt --from-file=config2.txt

# 3. 디렉토리 전체
k create cm app-config --from-file=/path/to/configs/

# 4. env 파일 (KEY=VALUE 형식)
k create cm app-config --from-env-file=config.env
```

### ConfigMap YAML

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  ENV: prod
  LOG_LEVEL: debug
  app.properties: |
    server.port=8080
    server.host=0.0.0.0
```

### 사용 방법 3가지

**방법 1: 환경변수로 (특정 key만)**

```yaml
spec:
  containers:
  - name: app
    image: nginx
    env:
    - name: ENVIRONMENT
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: ENV
```

**방법 2: 환경변수로 (전체)**

```yaml
spec:
  containers:
  - name: app
    image: nginx
    envFrom:
    - configMapRef:
        name: app-config
```

**방법 3: 볼륨으로 마운트 (파일로)**

```yaml
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: config-vol
      mountPath: /etc/config
      readOnly: true
  volumes:
  - name: config-vol
    configMap:
      name: app-config
      # 특정 key만 마운트
      items:
      - key: app.properties
        path: application.properties
```

볼륨 마운트 시 `/etc/config/` 아래에 각 key가 파일명, value가 파일 내용으로 생성됩니다.

## 3. Secret

민감한 데이터 저장용. 내용이 base64로 인코딩됩니다 (암호화 아님, 단순 인코딩).

### 생성 방법

```bash
# 1. literal
k create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password=s3cr3t

# 2. 파일에서
k create secret generic ssh-key --from-file=ssh-privatekey=/path/to/id_rsa

# 3. env 파일
k create secret generic db-secret --from-env-file=secret.env

# 4. TLS Secret
k create secret tls my-tls --cert=server.crt --key=server.key

# 5. Docker registry
k create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=user \
  --docker-password=pass \
  --docker-email=user@example.com
```

### Secret YAML

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque                    # 기본 type
data:
  username: YWRtaW4=            # base64로 인코딩된 값
  password: czNjcjN0
# 또는 plain text로
stringData:
  username: admin
  password: s3cr3t
```

`data`는 base64 인코딩 필수, `stringData`는 평문 그대로. 둘 다 결국 같은 결과.

### Secret Type 종류

|Type|용도|
|---|---|
|`Opaque`|일반 (기본값)|
|`kubernetes.io/tls`|TLS 인증서|
|`kubernetes.io/dockerconfigjson`|Docker registry 인증|
|`kubernetes.io/service-account-token`|SA 토큰|
|`kubernetes.io/basic-auth`|기본 인증|
|`kubernetes.io/ssh-auth`|SSH 인증|

### 사용 방법 3가지

ConfigMap과 거의 동일합니다.

**방법 1: 환경변수로 (특정 key만)**

```yaml
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: password
```

**방법 2: 환경변수로 (전체)**

```yaml
envFrom:
- secretRef:
    name: db-secret
```

**방법 3: 볼륨으로 마운트**

```yaml
volumes:
- name: secret-vol
  secret:
    secretName: db-secret
    defaultMode: 0400        # 권한 설정 가능
```

### base64 인코딩/디코딩

```bash
# 인코딩
echo -n "admin" | base64
# YWRtaW4=

# 디코딩
echo "YWRtaW4=" | base64 -d
# admin

# Secret 안의 값 직접 디코딩
k get secret db-secret -o jsonpath='{.data.password}' | base64 -d
```

`-n` 플래그를 빼면 줄바꿈이 인코딩에 포함되니 주의.

## 4. Resource Requirements

### requests / limits

```yaml
spec:
  containers:
  - name: app
    image: nginx
    resources:
      requests:           # 보장받는 최소 자원 (스케줄링 기준)
        cpu: "100m"        # 0.1 core
        memory: "128Mi"
      limits:             # 최대 사용 가능
        cpu: "500m"
        memory: "512Mi"
```

### 단위 정리

**CPU**:

- `1` = 1 core (1000 millicores)
- `500m` = 0.5 core
- `100m` = 0.1 core

**메모리**:

- `Mi`, `Gi` = 2진수 (1024 기반) ← 일반적
- `M`, `G` = 10진수 (1000 기반)
- `128Mi` ≠ `128M` (약 7% 차이)

### 동작 방식

|상황|CPU|Memory|
|---|---|---|
|`requests` 충족 안 됨|노드 스케줄링 안 됨|노드 스케줄링 안 됨|
|`limits` 초과|throttle (속도 제한)|OOMKilled (강제 종료)|

### 명령어로 설정

```bash
k set resources deploy/web \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=500m,memory=512Mi
```

### LimitRange (namespace 기본값)

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: mem-limit-range
spec:
  limits:
  - default:           # limits 미지정 시 적용
      memory: 512Mi
    defaultRequest:    # requests 미지정 시 적용
      memory: 256Mi
    type: Container
```

CKAD에서 가끔 LimitRange가 적용된 namespace에서 Pod 동작을 묻는 문제가 나옵니다.

## 5. SecurityContext

Pod 또는 Container 레벨에서 보안 설정을 합니다.

### Pod 레벨 vs Container 레벨

```yaml
spec:
  securityContext:              # Pod 레벨 (모든 컨테이너에 적용)
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    runAsNonRoot: true
  containers:
  - name: app
    image: nginx
    securityContext:            # Container 레벨 (Pod 레벨 덮어씀)
      runAsUser: 2000
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        add: ["NET_ADMIN", "SYS_TIME"]
        drop: ["ALL"]
      privileged: false
```

### 주요 필드

|필드|위치|의미|
|---|---|---|
|`runAsUser`|Pod/Container|실행할 UID|
|`runAsGroup`|Pod/Container|실행할 GID|
|`fsGroup`|Pod|볼륨 파일의 그룹 소유권|
|`runAsNonRoot`|Pod/Container|root 금지|
|`allowPrivilegeEscalation`|Container|권한 상승 금지|
|`readOnlyRootFilesystem`|Container|루트 FS 읽기 전용|
|`privileged`|Container|특권 모드 (호스트 자원 접근)|
|`capabilities.add/drop`|Container|리눅스 capability|

**Pod 레벨에만 있는 필드**: `fsGroup`, `supplementalGroups` **Container 레벨에만 있는 필드**: `capabilities`, `allowPrivilegeEscalation`, `readOnlyRootFilesystem`, `privileged`

### Capabilities

리눅스 권한을 세분화한 단위. 자주 쓰이는 것:

- `NET_ADMIN`: 네트워크 설정
- `NET_BIND_SERVICE`: 1024 이하 포트 바인딩
- `SYS_TIME`: 시스템 시간 변경
- `SYS_ADMIN`: 시스템 관리 (광범위)
- `CHOWN`: 파일 소유권 변경

## 6. ServiceAccount

Pod이 Kubernetes API와 통신할 때 사용하는 신원입니다.

### 생성과 할당

```bash
# 생성
k create sa my-sa
k create sa my-sa -n dev

# 토큰 생성 (1.24+)
k create token my-sa
```

Pod에 할당:

```yaml
spec:
  serviceAccountName: my-sa
  automountServiceAccountToken: false   # 토큰 자동 마운트 비활성화
  containers:
  - name: app
    image: nginx
```

### 기본 동작

- 모든 Pod은 자동으로 `default` SA를 가짐
- SA 토큰이 `/var/run/secrets/kubernetes.io/serviceaccount/`에 자동 마운트됨
- `automountServiceAccountToken: false`로 비활성화 가능

## 7. Env / Args / Command 정리

### 모든 환경변수 주입 방식

```yaml
spec:
  containers:
  - name: app
    image: my-app
    env:
    # 1. 직접 값
    - name: ENV
      value: "prod"
    # 2. ConfigMap에서
    - name: APP_CONFIG
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: config-key
    # 3. Secret에서
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
    # 4. Pod 정보 (Downward API)
    - name: POD_NAME
      valueFrom:
        fieldRef:
          fieldPath: metadata.name
    # 5. 리소스 정보 (Downward API)
    - name: CPU_LIMIT
      valueFrom:
        resourceFieldRef:
          containerName: app
          resource: limits.cpu
    
    envFrom:
    # 6. ConfigMap 전체
    - configMapRef:
        name: app-config
    # 7. Secret 전체
    - secretRef:
        name: db-secret
    # 8. Prefix 추가
    - prefix: APP_
      configMapRef:
        name: app-config
```

### Command / Args

```yaml
containers:
- name: app
  image: busybox
  command: ["sh", "-c"]                   # Docker ENTRYPOINT
  args: ["echo hello && sleep 3600"]      # Docker CMD
```

명령어로 생성:

```bash
# args만 (이미지 ENTRYPOINT 사용)
k run my-pod --image=busybox $do -- sleep 3600 > pod.yaml

# command 지정
k run my-pod --image=busybox --command $do -- /bin/sh -c "sleep 3600" > pod.yaml
```

## 8. ConfigMap/Secret 업데이트 시 동작

### 환경변수로 주입한 경우

- **Pod 재생성 전까지 변경 반영 안 됨**
- ConfigMap을 수정해도 이미 실행 중인 Pod의 환경변수는 그대로

### 볼륨으로 마운트한 경우

- **자동으로 업데이트됨** (수십 초 ~ 1분 지연)
- 단, `subPath`로 마운트한 경우는 업데이트 안 됨

이 차이는 시험에 가끔 함정으로 나옵니다.

## 출제 패턴

Configuration은 다음 8가지 유형으로 정형화되어 있습니다.

### 패턴 1: ConfigMap 생성 + Pod에 환경변수로 주입 (매번 출제)

"app-config ConfigMap을 만들고, Pod의 환경변수 APP_ENV로 ENV 값을 주입하라."

```bash
k create cm app-config --from-literal=ENV=prod --from-literal=LOG=debug
```

```yaml
env:
- name: APP_ENV
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: ENV
```

### 패턴 2: Secret 생성 + Pod에 주입

"db-secret을 만들고, Pod의 환경변수 DB_PASSWORD로 password 값을 주입하라."

```bash
k create secret generic db-secret --from-literal=password=s3cr3t
```

```yaml
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: password
```

### 패턴 3: ConfigMap을 볼륨으로 마운트

"app-config의 내용을 Pod의 /etc/config 디렉토리에 마운트하라."

```yaml
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: config
      mountPath: /etc/config
      readOnly: true
  volumes:
  - name: config
    configMap:
      name: app-config
```

검증: `k exec my-pod -- ls /etc/config`

### 패턴 4: Resources 설정

"requests cpu=100m memory=128Mi, limits cpu=500m memory=512Mi로 설정하라."

```bash
k set resources deploy/web --requests=cpu=100m,memory=128Mi --limits=cpu=500m,memory=512Mi
```

또는 YAML 직접:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

### 패턴 5: SecurityContext 설정

"Pod를 UID 1000으로 실행하고, NET_ADMIN capability를 추가하고, privilege escalation을 금지하라."

```yaml
spec:
  securityContext:
    runAsUser: 1000
  containers:
  - name: app
    image: nginx
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        add: ["NET_ADMIN"]
```

**중요**: `runAsUser`는 Pod 레벨에서, `capabilities`는 Container 레벨에서. 위치를 헷갈리면 안 됨.

### 패턴 6: ServiceAccount 생성 및 할당

"my-sa를 만들고 web Deployment의 모든 Pod이 이 SA를 사용하게 하라."

```bash
k create sa my-sa
k set serviceaccount deploy/web my-sa
```

검증: `k get pod -o jsonpath='{.items[*].spec.serviceAccountName}'`

### 패턴 7: ConfigMap/Secret 전체를 envFrom으로

"app-config의 모든 key를 환경변수로 주입하라."

```yaml
envFrom:
- configMapRef:
    name: app-config
- secretRef:
    name: db-secret
```

### 패턴 8: Command / Args 변경

"Pod의 명령어를 sleep 3600으로 바꿔라."

```yaml
containers:
- name: app
  image: busybox
  command: ["sleep", "3600"]
```

또는 imperative:

```bash
k run my-pod --image=busybox $do -- sleep 3600 > pod.yaml
```

## 함정 포인트

### 함정 1 — Secret의 base64

```yaml
# data 사용 시 base64 인코딩 필수
data:
  password: czNjcjN0          # echo -n "s3cr3t" | base64

# stringData 사용 시 평문
stringData:
  password: s3cr3t
```

YAML 직접 작성 시 `data`와 `stringData`를 헷갈리지 마세요. 둘 다 결과는 같지만 입력 형식이 다릅니다.

### 함정 2 — `echo -n` 빠뜨림

```bash
echo "admin" | base64        # ❌ 줄바꿈 포함 → YWRtaW4K
echo -n "admin" | base64     # ✅ YWRtaW4=
```

`-n` 누락이 가장 흔한 실수.

### 함정 3 — ConfigMap key 이름

```yaml
configMapKeyRef:
  name: app-config
  key: ENV               # ConfigMap에 정확히 이 key가 있어야 함
```

ConfigMap에 `env`로 되어 있는데 `ENV`로 참조하면 에러. 대소문자 구분.

### 함정 4 — SecurityContext 위치

```yaml
# capabilities는 Container 레벨에만
spec:
  securityContext:
    capabilities:          # ❌ Pod 레벨에 두면 무시됨
      add: ["NET_ADMIN"]
  containers:
  - name: app
    securityContext:
      capabilities:        # ✅ 여기에 둬야 적용
        add: ["NET_ADMIN"]
```

|필드|Pod 레벨|Container 레벨|
|---|---|---|
|`runAsUser`|✅|✅|
|`runAsGroup`|✅|✅|
|`runAsNonRoot`|✅|✅|
|`fsGroup`|✅|❌|
|`capabilities`|❌|✅|
|`allowPrivilegeEscalation`|❌|✅|
|`readOnlyRootFilesystem`|❌|✅|
|`privileged`|❌|✅|

### 함정 5 — Container 레벨이 Pod 레벨 덮어씀

```yaml
spec:
  securityContext:
    runAsUser: 1000     # Pod 기본값
  containers:
  - name: app
    securityContext:
      runAsUser: 2000   # 이 컨테이너만 2000 (override)
```

문제에서 "이 컨테이너만"이라고 하면 Container 레벨에, "모든 컨테이너"라고 하면 Pod 레벨에.

### 함정 6 — Resource 단위 헷갈림

```yaml
memory: 128M     # 10진수 (128,000,000)
memory: 128Mi    # 2진수 (128 * 1024 * 1024) ← 일반적
cpu: 1           # 1 core
cpu: 1000m       # 1 core (같음)
cpu: 100m        # 0.1 core
```

시험에서는 거의 항상 `Mi`, `Gi`. CPU는 `m` 단위.

### 함정 7 — ConfigMap/Secret 업데이트 반영

```yaml
# 환경변수로 주입 → Pod 재생성 전까지 반영 안 됨
env:
- name: ENV
  valueFrom:
    configMapKeyRef: ...

# 볼륨으로 마운트 → 자동 업데이트됨 (수십 초 후)
volumes:
- name: config
  configMap:
    name: app-config
```

문제에서 "ConfigMap을 수정하면 Pod에 반영되어야 한다"고 하면 볼륨 마운트 방식 선택.

### 함정 8 — `automountServiceAccountToken`

```yaml
spec:
  serviceAccountName: my-sa
  automountServiceAccountToken: false   # SA는 할당하되 토큰 마운트 안 함
```

특정 보안 요구사항에서 토큰을 안 마운트하라는 문제가 가끔 출제됨.

### 함정 9 — envFrom의 key는 환경변수명

```yaml
# ConfigMap data:
#   LOG_LEVEL: debug
#   server.port: 8080      ← 점이 들어가면 env로 못 씀

envFrom:
- configMapRef:
    name: app-config
# → 환경변수 LOG_LEVEL=debug 만 생성됨
# → server.port는 invalid env name이라 스킵됨
```

`envFrom`은 key 이름이 환경변수 명명 규칙(영문/숫자/언더스코어)을 따라야 함. 점이나 하이픈 있으면 환경변수로 안 생김.

### 함정 10 — `subPath` 마운트는 자동 업데이트 안 됨

```yaml
volumeMounts:
- name: config
  mountPath: /etc/nginx/nginx.conf
  subPath: nginx.conf       # 특정 파일만 마운트
```

`subPath` 사용 시 ConfigMap이 바뀌어도 자동 업데이트가 안 됩니다.

### 함정 11 — runAsNonRoot + image의 root 충돌

```yaml
securityContext:
  runAsNonRoot: true
```

이 설정에서 이미지가 root로 실행되도록 빌드됐다면 Pod이 시작 안 됨. 에러 메시지: `container has runAsNonRoot and image will run as root`. 이미지를 바꾸거나 `runAsUser`로 명시적 UID 지정.

### 함정 12 — Pod의 immutable 필드

Pod의 `env`, `resources`, `securityContext`는 수정 불가. Deployment에서 수정해야 새 Pod이 생성됨. 직접 Pod을 수정하려면 삭제 후 재생성.

## 디버깅 명령

```bash
# ConfigMap / Secret 내용 확인
k get cm app-config -o yaml
k describe cm app-config
k get secret db-secret -o yaml
k get secret db-secret -o jsonpath='{.data.password}' | base64 -d

# Pod의 환경변수 확인
k exec my-pod -- env
k exec my-pod -- env | grep DB_

# Pod의 마운트된 파일 확인
k exec my-pod -- ls /etc/config
k exec my-pod -- cat /etc/config/app.properties

# Pod의 현재 SecurityContext
k get pod my-pod -o jsonpath='{.spec.securityContext}'
k get pod my-pod -o jsonpath='{.spec.containers[0].securityContext}'

# SA 확인
k get pod my-pod -o jsonpath='{.spec.serviceAccountName}'

# Resource 사용량
k top pod my-pod
k describe pod my-pod | grep -A 5 Limits
```

## 빠르게 작성하는 팁

- **ConfigMap/Secret은 거의 항상 `k create cm/secret`** 으로 생성. YAML 직접 안 씀.
- **Pod에 주입은 YAML 작성 필수**. `k run`으로 골격을 만들고 env/envFrom/volumeMounts 추가.
- **Resources는 명령어로**: `k set resources` 가 가장 빠름.
- **Env 추가도 명령어로**: `k set env deploy/web KEY=value`.
- **SA 할당도 명령어로**: `k set serviceaccount deploy/web my-sa`.
- **base64 인코딩이 필요할 때**:
    
    ```bash
    echo -n "value" | base64
    ```
    
    꼭 `-n` 붙이기.
- **시크릿 값 빠르게 디코딩**:
    
    ```bash
    k get secret db-secret -o jsonpath='{.data.password}' | base64 -d
    ```
    
- **설정 적용 후 검증 필수**: `k exec my-pod -- env`로 환경변수가 제대로 들어갔는지, `ls /etc/config`으로 파일이 마운트됐는지 확인.
- **SecurityContext는 YAML 직접 작성**. 명령어로 안 됨. 빈 템플릿 외워두기.

## 자주 헷갈리는 차이 정리

|항목|ConfigMap|Secret|
|---|---|---|
|용도|일반 설정|민감 정보|
|인코딩|평문|base64|
|암호화|❌|❌ (단순 인코딩)|
|크기 제한|1 MiB|1 MiB|
|사용 방법|동일 (env/envFrom/volume)|동일|

|주입 방식|장점|단점|
|---|---|---|
|`env` (개별)|명시적, 이름 변경 가능|여러 개면 장황|
|`envFrom` (전체)|간결|이름 변경 불가, invalid name 스킵|
|`volumeMount` (파일)|자동 업데이트 가능, 큰 파일 OK|앱이 파일 읽기 지원해야 함|

|환경변수 출처|키워드|
|---|---|
|직접 값|`value`|
|ConfigMap의 특정 key|`valueFrom.configMapKeyRef`|
|Secret의 특정 key|`valueFrom.secretKeyRef`|
|Pod 메타 정보|`valueFrom.fieldRef`|
|리소스 정보|`valueFrom.resourceFieldRef`|
|ConfigMap 전체|`envFrom.configMapRef`|
|Secret 전체|`envFrom.secretRef`|

|리소스 단위|의미|
|---|---|
|`1` (CPU)|1 core|
|`500m` (CPU)|0.5 core|
|`100m` (CPU)|0.1 core|
|`Mi` (Memory)|2진수 (1024 기반)|
|`Gi` (Memory)|2진수 (1024 * 1024 * 1024)|
|`M` (Memory)|10진수 (1000 기반)|

|SecurityContext 필드|Pod 레벨|Container 레벨|
|---|---|---|
|`runAsUser`|✅|✅|
|`runAsGroup`|✅|✅|
|`runAsNonRoot`|✅|✅|
|`fsGroup`|✅|❌|
|`capabilities`|❌|✅|
|`allowPrivilegeEscalation`|❌|✅|
|`readOnlyRootFilesystem`|❌|✅|
|`privileged`|❌|✅|

---

Configuration은 **출제 빈도가 매우 높고 변형이 다양한 영역**입니다. ConfigMap/Secret의 3가지 주입 방식(env/envFrom/volume), SecurityContext의 Pod vs Container 레벨 차이, Resources의 단위, base64 인코딩 명령은 머리에 완전히 박힐 때까지 반복 연습하세요. 특히 `k create cm/secret` 명령어 옵션과 `k set env/resources/serviceaccount` 명령은 시간 절약 효과가 가장 큰 도구들이니 손에 익혀두면 좋습니다.
