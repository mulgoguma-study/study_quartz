### 출제 패턴

#### 패턴 1: Deployment를 Service로 노출 (매번 출제)

"web Deployment를 ClusterIP Service로 노출, 포트 80→8080."


```bash
k expose deploy web --port=80 --target-port=8080
k get svc web
k get ep web      # Pod에 제대로 연결됐는지 확인
```

#### 패턴 2: NodePort로 외부 노출

"NodePort 30080으로 외부에서 접근 가능하게 하라."

```bash
k expose deploy web --port=80 --target-port=8080 --type=NodePort
# nodePort를 30080으로 지정해야 하면 YAML 수정
k edit svc web
```

```yaml
ports:
- port: 80
  targetPort: 8080
  nodePort: 30080
```

#### 패턴 3: Service로 Pod 접근 테스트

"임시 Pod에서 my-svc로 curl/wget 해서 응답을 확인하라."

```bash
k run tmp --image=busybox --rm -it --restart=Never -- wget -O- my-svc:80
k run tmp --image=curlimages/curl --rm -it --restart=Never -- curl my-svc.prod:80
```

#### 패턴 4: Ingress 생성

"example.com/api → api-svc:80, example.com/web → web-svc:80으로 라우팅하는 Ingress를 만들어라."


```bash
k create ingress my-ing \
  --rule="example.com/api*=api-svc:80" \
  --rule="example.com/web*=web-svc:80"
```

#### 패턴 5: NetworkPolicy로 트래픽 제한

"frontend namespace의 Pod만 backend Pod의 8080 포트로 접근 가능. 그 외 모두 차단."

YAML 직접 작성. namespace selector + pod selector 조합 주의.

#### 패턴 6: Endpoints 디버깅

"Service를 만들었는데 트래픽이 안 가는데 원인을 찾아라."

```bash
k get svc my-svc
k get ep my-svc           # 비어있으면 selector 문제
k describe svc my-svc
k get pod --show-labels   # 라벨 일치 확인
```

### 함정 포인트

#### 함정 1 — port vs targetPort 혼동

```yaml
ports:
- port: 80          # 클라이언트가 접근하는 포트 (Service)
  targetPort: 8080  # Pod에 도달하는 포트 (Container)
```

문제에서 "Pod이 8080 포트를 listen, Service는 80 포트로 노출"이라 하면 `port: 80, targetPort: 8080`. 반대로 쓰면 트래픽 전달 실패.

#### 함정 2 — Service selector와 Pod label 불일치

```yaml
# Service
selector:
  app: web

# Pod
labels:
  app: webserver   # ❌ 불일치 → Endpoints 비어있음
```

`k expose deploy`로 만들면 자동으로 맞춰지지만, 직접 YAML 작성하면 자주 실수.

#### 함정 3 — NodePort 범위

`nodePort`는 **30000-32767** 범위만 가능. 30080은 가능, 8080은 불가.

#### 함정 4 — `targetPort`는 이름도 가능

```yaml
# Pod
ports:
- containerPort: 8080
  name: http

# Service
ports:
- port: 80
  targetPort: http   # 이름으로도 참조 가능
```

#### 함정 5 — NetworkPolicy의 AND/OR

dash 위치가 결정적입니다.

```yaml
# OR: frontend Pod 이거나 prod namespace의 모든 Pod
- from:
  - podSelector:
      matchLabels:
        app: frontend
  - namespaceSelector:
      matchLabels:
        env: prod

# AND: prod namespace의 frontend Pod만
- from:
  - namespaceSelector:
      matchLabels:
        env: prod
    podSelector:
      matchLabels:
        app: frontend
```

CKAD의 NetworkPolicy 문제에서 가장 자주 묻는 부분.

#### 함정 6 — policyTypes 누락


```yaml
spec:
  policyTypes:
  - Ingress
  # Egress가 없으면 egress 규칙은 무시됨
  ingress: ...
  egress: ...   # 이건 적용 안 됨
```

명시적으로 둘 다 적어야 합니다.

#### 함정 7 — Egress 차단 시 DNS 끊김

Egress를 모두 deny하면 DNS(UDP 53)도 막혀서 Pod이 통신 불가. kube-system의 DNS Pod을 허용해야 함.

```yaml
egress:
- to:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: kube-system
  ports:
  - protocol: UDP
    port: 53
```

#### 함정 8 — 빈 selector의 의미


```yaml
# 빈 podSelector: 해당 namespace의 모든 Pod
podSelector: {}

# 빈 from: 모든 트래픽 허용
- from: []
# 또는 from 자체를 생략
ingress:
- ports: ...
```

빈 객체 `{}`와 생략은 다른 의미. 주의.

#### 함정 9 — Ingress의 pathType 필수

```yaml
paths:
- path: /api
  pathType: Prefix   # ✅ 필수 (1.18+)
  backend: ...
```

`pathType`을 빼면 일부 컨트롤러에서 라우팅 실패. 거의 항상 `Prefix` 사용.

#### 함정 10 — Ingress의 backend service 포트는 number 또는 name


```yaml
backend:
  service:
    name: api-svc
    port:
      number: 80    # 숫자로
      # 또는
      name: http    # 이름으로 (Service의 port name)
```

둘 중 하나만. 동시에 쓰면 안 됨.
