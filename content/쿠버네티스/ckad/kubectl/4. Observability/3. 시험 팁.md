
# Observability 시험 팁

## 시작 세팅

```bash
alias k=kubectl
export do="--dry-run=client -o yaml"
```

## 자주 쓰는 명령 요약

### Probes (YAML에 직접 추가)

명령어로 probe 추가하는 방법은 없습니다. **항상 YAML 수정**.

```bash
# Pod 골격 생성
k run my-pod --image=nginx $do > pod.yaml
# vi pod.yaml로 probe 추가
```

빠르게 외울 빈 템플릿:

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 80
  initialDelaySeconds: 10
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /ready
    port: 80
  initialDelaySeconds: 5
  periodSeconds: 3
```

```yaml
# Exec 방식
livenessProbe:
  exec:
    command: ["cat", "/tmp/healthy"]
  initialDelaySeconds: 5
  periodSeconds: 5

# TCP 방식
livenessProbe:
  tcpSocket:
    port: 80
  initialDelaySeconds: 10
```

### Logs (가장 자주 쓰는 명령)

```bash
k logs my-pod
k logs my-pod -c <container>
k logs my-pod --previous              # ← 크래시 디버깅의 핵심
k logs my-pod -f --tail=20
k logs my-pod --since=5m
k logs -l app=web                     # 라벨로 여러 Pod
k logs deploy/web
k logs my-pod > /tmp/pod.log          # 파일 저장
```

### Metrics

```bash
k top pod
k top pod -A
k top pod --sort-by=cpu
k top pod --sort-by=memory
k top pod my-pod --containers
k top node
```

### Describe / Events

```bash
k describe pod my-pod
k describe pod my-pod | grep -A 10 Events
k get events --sort-by=.metadata.creationTimestamp
k get events --field-selector involvedObject.name=my-pod
k get events --field-selector type=Warning
```

## explain으로 확인할 필드

```bash
# Probe 필드 (가장 자주 확인)
k explain pod.spec.containers.livenessProbe
k explain pod.spec.containers.readinessProbe
k explain pod.spec.containers.startupProbe
k explain pod.spec.containers.livenessProbe --recursive

# 모든 probe 옵션 한 번에
k explain pod.spec.containers.livenessProbe.httpGet
k explain pod.spec.containers.livenessProbe.exec
k explain pod.spec.containers.livenessProbe.tcpSocket
```

Probe 필드명이 길고 헷갈리니 시험장에서 explain 적극 활용.


이 순서를 머리에 박아두면 어떤 디버깅 문제든 1분 안에 원인 파악 가능.

## 빠르게 작성하는 팁

- **Probe는 항상 YAML 직접 작성**. 빈 템플릿(HTTP/Exec/TCP) 3개를 머리에 외워두고 즉시 입력.
- **`k edit deploy <name>` 후 probe 추가**가 가장 빠른 적용 방법. 저장하면 즉시 새 ReplicaSet으로 rolling update.
- **로그는 `--previous`를 기본 옵션처럼 생각**. CrashLoop 디버깅에선 무조건.
- **`describe` 결과는 항상 Events 섹션부터 읽기**. 90%의 원인이 거기 있음.
- **`top pod --sort-by=` 결과 가공**: 시험에선 파일에 이름 하나만 저장하라는 식. `head -1 | awk '{print $1}'` 패턴 외워두기.
- **`k logs -l <label>`**: 여러 Pod의 로그를 한 번에 보고 싶을 때.
- **probe 적용 후 검증 필수**: `k get pod`의 RESTARTS 컬럼이 늘어나면 probe가 잘못된 것. 즉시 수정.
- **`--all-containers`**: multi-container에서 어느 컨테이너가 문제인지 모를 때 한 번에 전체 로그.

## 자주 헷갈리는 차이 정리

|항목|Liveness|Readiness|Startup|
|---|---|---|---|
|실패 시|컨테이너 재시작|endpoint 제거|컨테이너 재시작|
|사용 시점|운영 중 계속|운영 중 계속|시작 시만|
|워밍업용?|❌|✅|✅|
|데드락 감지|✅|❌|❌|
|successThreshold|1 고정|변경 가능|1 고정|
|다른 probe와 관계|독립|독립|성공 전엔 다른 probe 비활성|

|명령|용도|핵심 옵션|
|---|---|---|
|`k logs`|현재 로그|`-c`, `--previous`, `-f`, `--tail`, `--since`|
|`k describe`|상세 + 이벤트|(옵션 거의 없음)|
|`k get events`|클러스터 이벤트|`--sort-by`, `--field-selector`|
|`k top`|메트릭|`--sort-by`, `--containers`, `-A`|
|`k exec`|컨테이너 접속|`-it`, `-c`|

| 종료 Reason            | 의미       | 다음 행동           |
| -------------------- | -------- | --------------- |
| `Error`              | 비정상 종료   | logs로 앱 에러 확인   |
| `OOMKilled`          | 메모리 초과   | memory limit 증가 |
| `Completed`          | 정상 종료    | Job이면 정상        |
| `ContainerCannotRun` | 명령 실행 실패 | command/args 확인 |
| `CrashLoopBackOff`   | 반복 크래시   | logs --previous |

|Probe 방식|적합한 경우|
|---|---|
|`httpGet`|HTTP API 서버 (가장 흔함)|
|`tcpSocket`|DB, Redis 등 TCP 서비스|
|`exec`|커스텀 헬스체크 스크립트|

---

Observability는 **명령어 숙련도가 곧 점수**인 영역입니다. Probe는 YAML 템플릿 3개(HTTP/Exec/TCP)를 외우고, 디버깅은 `get → describe → logs --previous → exec → events` 흐름을 머리에 박아두세요. 특히 `--previous` 옵션, multi-container의 `-c`, probe의 `initialDelaySeconds` 적정값 이 세 가지는 가장 자주 실수하는 부분이니 시험 직전에 다시 한 번 복습하세요.
