
## 1. Observability란

운영 중인 애플리케이션의 상태를 **관찰하고 진단**하는 능력입니다. Kubernetes에서는 크게 세 가지 도구로 구성됩니다.

- **Probes**: 컨테이너가 정상인지 자동 검사
- **Logs**: 컨테이너의 stdout/stderr 확인
- **Metrics**: CPU/메모리 등 리소스 사용량 확인

여기에 `describe`, `events` 같은 진단 명령이 더해집니다.

## 2. Probes (Health Checks)

### 3종류의 Probe

|Probe|목적|실패 시 동작|
|---|---|---|
|**Liveness**|살아있는가?|컨테이너 재시작|
|**Readiness**|트래픽 받을 준비?|Service endpoint에서 제거|
|**Startup**|시작이 완료됐는가?|컨테이너 재시작 (성공 전엔 다른 probe 비활성)|

### Probe 동작 방식 3가지

```yaml
# 1. HTTP GET
livenessProbe:
  httpGet:
    path: /healthz
    port: 80
    httpHeaders:
    - name: Custom-Header
      value: Awesome

# 2. TCP Socket
livenessProbe:
  tcpSocket:
    port: 80

# 3. Exec (명령 실행, 종료 코드 0이면 성공)
livenessProbe:
  exec:
    command:
    - cat
    - /tmp/healthy
```

### Probe의 타이밍 파라미터

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 80
  initialDelaySeconds: 10   # 첫 체크 전 대기 (기본 0)
  periodSeconds: 5          # 체크 주기 (기본 10)
  timeoutSeconds: 1         # 응답 대기 시간 (기본 1)
  failureThreshold: 3       # 연속 실패 허용 (기본 3)
  successThreshold: 1       # 성공으로 간주할 연속 성공 (기본 1)
```

**각 파라미터의 의미**:

- `initialDelaySeconds`: 앱이 시작될 시간을 줌. 0이면 즉시 체크
- `periodSeconds`: 너무 짧으면 부하, 너무 길면 감지 지연
- `failureThreshold`: 일시적 실패에 너그럽게. 3이면 3번 연속 실패해야 컨테이너 재시작
- `successThreshold`: Liveness/Startup은 반드시 1, Readiness만 1보다 큰 값 가능

### Liveness vs Readiness 차이

**Liveness**: "이 컨테이너 죽었나? 살려야 하나?"

- 무한 루프, 데드락 같은 회복 불가능한 상태 감지
- 실패 → kubelet이 컨테이너를 죽이고 재시작

**Readiness**: "지금 요청 받을 수 있나?"

- 시작 직후의 워밍업, 외부 의존성 일시 장애
- 실패 → Service endpoint에서 제외 (Pod은 살아있음)

```yaml
spec:
  containers:
  - name: app
    image: my-app
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 15
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 3
```

### Startup Probe

시작이 매우 느린 앱(JVM, 레거시)을 위한 probe. 성공하기 전까지는 liveness/readiness가 비활성화됩니다.

```yaml
startupProbe:
  httpGet:
    path: /started
    port: 8080
  failureThreshold: 30      # 30번 실패까지 허용
  periodSeconds: 10         # 10초마다 → 최대 300초 대기
```

이 시간 안에 성공하면 정상, 못 하면 컨테이너 재시작.

## 3. Logs

### 기본 명령

```bash
# Pod의 로그
k logs my-pod

# Multi-container Pod (컨테이너 이름 필수)
k logs my-pod -c app
k logs my-pod -c sidecar

# 모든 컨테이너 로그 합쳐서
k logs my-pod --all-containers

# 이전(크래시 전) 로그 — 디버깅 핵심
k logs my-pod --previous
k logs my-pod -c app --previous

# 실시간 (follow)
k logs my-pod -f
k logs my-pod -f --tail=10

# 마지막 N줄
k logs my-pod --tail=100

# 시간 기준
k logs my-pod --since=10m
k logs my-pod --since=1h
k logs my-pod --since-time=2026-05-21T10:00:00Z

# 타임스탬프 포함
k logs my-pod --timestamps

# Deployment / Job의 Pod 로그
k logs deploy/web                   # 첫 번째 Pod
k logs job/my-job
k logs -l app=web                   # 라벨 매칭되는 모든 Pod
k logs -l app=web --max-log-requests=10

# 파일로 저장
k logs my-pod > pod.log
```

### CrashLoopBackOff 디버깅

크래시한 Pod의 이전 로그를 보는 게 핵심입니다.

```bash
# 현재 로그 (재시작 후)
k logs my-pod

# 이전 인스턴스의 로그 ← 크래시 원인이 여기 있음
k logs my-pod --previous

# describe로 종료 코드와 마지막 상태 확인
k describe pod my-pod
```

`describe`에서 다음을 확인:

- `Last State`: 이전 종료 상태 (`Terminated`, exit code)
- `Reason`: `Error`, `OOMKilled`, `CrashLoopBackOff` 등
- `Restart Count`: 재시작 횟수

## 4. Metrics (kubectl top)

metrics-server가 설치되어 있어야 동작. CKAD 시험 환경에는 보통 설치되어 있습니다.

```bash
# Pod 리소스 사용량
k top pod
k top pod -A                    # 모든 namespace
k top pod -n kube-system

# 정렬
k top pod --sort-by=cpu
k top pod --sort-by=memory

# 라벨 필터
k top pod -l app=web

# 컨테이너별
k top pod my-pod --containers

# Node 리소스 사용량
k top node
k top node --sort-by=cpu
```

**활용**:

- CPU/Memory 사용량이 높은 Pod 찾기
- Resource limits 적정 값 산정
- OOMKilled 원인 분석

## 5. Describe / Events

### describe — 상세 정보의 핵심

```bash
k describe pod my-pod
k describe deploy web
k describe svc my-svc
k describe node worker-1
```

`describe pod`에서 확인해야 할 핵심 섹션:

```
Status: Running
Containers:
  app:
    Image: nginx:1.25
    State: Running
    Last State: Terminated         ← 이전 종료 정보
      Reason: Error
      Exit Code: 1
      Started: ...
      Finished: ...
    Ready: True
    Restart Count: 5               ← 자주 죽었다는 신호
    Liveness: http-get ...
    Readiness: http-get ...
Conditions:
  PodScheduled: True
  Initialized: True
  ContainersReady: True
  Ready: True
Events:                            ← 가장 유용한 섹션
  Warning  Failed   2m   kubelet  Liveness probe failed: ...
  Normal   Killing  1m   kubelet  Container app failed liveness probe
```

### events — 클러스터 이벤트

```bash
# 모든 이벤트 (최신순)
k get events --sort-by=.metadata.creationTimestamp

# 특정 리소스의 이벤트
k get events --field-selector involvedObject.name=my-pod

# 특정 namespace
k get events -n prod

# 모든 namespace
k get events -A

# Warning만
k get events --field-selector type=Warning
```

이벤트는 기본 1시간 후 삭제됩니다. 문제 발생 직후 빨리 확인해야 합니다.

## 6. Pod 상태 / Container 상태

### Pod Phase (5가지)

- `Pending`: 스케줄링 대기 또는 이미지 pull 중
- `Running`: 노드 할당 + 컨테이너 실행 중
- `Succeeded`: 모든 컨테이너 정상 종료 (Job용)
- `Failed`: 컨테이너가 비정상 종료
- `Unknown`: 노드 통신 불가

### 자주 보는 STATUS (Phase는 아님)

|STATUS|의미|주 원인|
|---|---|---|
|`ContainerCreating`|컨테이너 생성 중|정상 진행 중|
|`ImagePullBackOff`|이미지 pull 실패|이미지 오타, 사설 registry 인증|
|`ErrImagePull`|이미지 pull 실패 (초기)|동일|
|`CrashLoopBackOff`|반복 크래시|앱 에러, 잘못된 명령|
|`Error`|컨테이너 에러 종료|앱 종료 코드 비정상|
|`OOMKilled`|메모리 초과로 종료|limits 부족 또는 메모리 누수|
|`Completed`|Job의 정상 종료|Job 성공|
|`Init:0/2`|init container 진행 중|정상|
|`Init:Error`|init container 실패|init 명령 에러|
|`Pending`|스케줄링 대기|자원 부족, taint, nodeSelector|
|`Terminating`|삭제 중|grace period 진행 중|

### Conditions

```bash
k get pod my-pod -o jsonpath='{.status.conditions}'
```

- `PodScheduled`: 노드 할당됨
- `Initialized`: init container 완료
- `ContainersReady`: 모든 컨테이너 준비됨
- `Ready`: Service 트래픽 받을 준비됨

`Ready: False`라면 readinessProbe 실패 의심.
