## Readiness vs Liveness Probe

### 한 줄 개념

||목적|
|---|---|
|**Liveness**|이 컨테이너 살아있나? (죽었으면 재시작)|
|**Readiness**|이 컨테이너 트래픽 받을 준비됐나? (안됐으면 트래픽 차단)|

---

### Liveness Probe

컨테이너가 **데드락** 걸리거나 **좀비 상태**일 때 감지해서 재시작.

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10  # 컨테이너 뜨고 10초 후 시작
  periodSeconds: 5          # 5초마다 체크
  failureThreshold: 3       # 3번 실패하면 재시작
```

**실패하면** → 컨테이너 재시작 (Pod는 유지)

---

### Readiness Probe

컨테이너가 **완전히 준비되기 전까지** Service 엔드포인트에서 제외.

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 3
  failureThreshold: 3
```

**실패하면** → 재시작 없이 트래픽만 차단 (Pod는 Running 유지)

---

### 둘의 차이 핵심

```
Go 앱 시작
    ↓
DB 커넥션 맺는 중... (5초 소요)
    ↓
Readiness 실패 → 트래픽 안 받음 (정상)
Liveness 실패 → 재시작 (아직 준비중인데 죽여버림 ❌)
    ↓
DB 커넥션 완료
    ↓
Readiness 성공 → 트래픽 받기 시작
```

그래서 보통 **initialDelaySeconds를 Liveness > Readiness** 로 설정함.

---

### 프로브 타입 3가지

```yaml
# 1. HTTP (가장 많이 씀)
httpGet:
  path: /health
  port: 8080

# 2. TCP
tcpSocket:
  port: 8080

# 3. 명령어 실행 (exit 0 이면 성공)
exec:
  command:
  - cat
  - /tmp/healthy
```

---

### Go 앱에서 구현 예시

```go
// Liveness - 앱이 살아있는지만 체크
http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
})

// Readiness - DB 연결 등 실제 준비 상태 체크
http.HandleFunc("/ready", func(w http.ResponseWriter, r *http.Request) {
    if err := db.Ping(); err != nil {
        w.WriteHeader(http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
})
```

---

### 한 줄 요약

```
Liveness  = 심장박동 체크 (멈추면 재시작)
Readiness = 출근 준비 체크 (준비 안됐으면 업무 안 줌)
```




CKAD 시험 스타일로 보여줄게.

---

**문제**

```
Context:
namespace: web-app

Task:
1. pod 이름: web-server
2. image: nginx
3. Liveness Probe 설정
   - HTTP GET /healthz port 8080
   - 초기 대기: 15초
   - 체크 주기: 10초
4. Readiness Probe 설정
   - HTTP GET /ready port 8080
   - 초기 대기: 5초
   - 체크 주기: 5초
   - 3번 실패시 트래픽 차단
```

---

**풀이 - 빠른 접근법**

```bash
#### 1. dry-run으로 기본 yaml 생성
kubectl run web-server \
  --image=nginx \
  --dry-run=client \
  -o yaml \
  -n web-app > pod.yaml
```

```bash
#### 2. yaml 편집
vi pod.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-server
  namespace: web-app
spec:
  containers:
  - name: web-server
    image: nginx
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 15
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5
      failureThreshold: 3
```

```bash
#### 3. 적용
kubectl apply -f pod.yaml

#### 4. 확인 (시험에서 꼭 검증해야 점수 받음)
kubectl describe pod web-server -n web-app | grep -A 10 Liveness
kubectl describe pod web-server -n web-app | grep -A 10 Readiness
```

---

**시험에서 자주 나오는 변형**

```
- 기존 Deployment에 probe 추가하라
- probe 실패해서 재시작 중인 Pod 트러블슈팅
- exec 타입 probe 설정 (httpGet 대신 명령어)
```

---

**트러블슈팅 문제 예시**

```
Task:
web-app namespace의 api-server Pod가 계속 재시작되고 있다.
원인을 찾고 수정하라.
```

```bash
#### 접근법
kubectl get pod api-server -n web-app   # RESTARTS 확인
kubectl describe pod api-server -n web-app  # Events에서 원인 확인
kubectl logs api-server -n web-app --previous  # 이전 컨테이너 로그

#### 보통 이런 원인들
#### - livenessProbe path가 틀림 (/health vs /healthz)
#### - initialDelaySeconds가 너무 짧아서 앱 뜨기 전에 실패
#### - port가 잘못됨
```

**시험 팁**

`describe` 에서 이 부분 꼭 확인하는 습관 들이기:

