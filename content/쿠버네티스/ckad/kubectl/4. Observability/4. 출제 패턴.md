

## 출제 패턴

Observability는 다음 6가지 유형으로 정형화되어 있습니다.

### 패턴 1: Liveness Probe 추가 (가장 자주 출제)

"기존 Deployment에 HTTP /healthz로 liveness probe를 추가하라. 첫 체크는 10초 후, 5초마다."

```bash
k edit deploy web
```

```yaml
containers:
- name: app
  image: nginx
  livenessProbe:
    httpGet:
      path: /healthz
      port: 80
    initialDelaySeconds: 10
    periodSeconds: 5
```

### 패턴 2: Readiness Probe 추가

"앱이 준비될 때까지 트래픽을 받지 않게 readiness probe를 설정하라."

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 3
```

### 패턴 3: Exec 방식 Probe

"`/tmp/healthy` 파일이 있을 때만 정상으로 인식하는 liveness probe를 만들어라."

```yaml
livenessProbe:
  exec:
    command:
    - cat
    - /tmp/healthy
  initialDelaySeconds: 5
  periodSeconds: 5
```

### 패턴 4: 로그에서 특정 문자열 찾기

"Pod의 로그에서 'ERROR' 라인을 찾아 파일로 저장하라."

```bash
k logs my-pod | grep ERROR > /opt/errors.txt
k logs my-pod | grep -i error > /opt/errors.txt
```

라벨로 여러 Pod에서:

```bash
k logs -l app=web --tail=-1 | grep ERROR > /opt/errors.txt
```

### 패턴 5: 리소스 사용량 가장 높은 Pod 찾기

"CPU 사용량이 가장 높은 Pod의 이름을 파일에 기록하라."

```bash
k top pod -A --sort-by=cpu | head -2 | tail -1 | awk '{print $2}' > /opt/top-cpu.txt

# 또는 한 namespace 안에서
k top pod --sort-by=cpu --no-headers | head -1 | awk '{print $1}' > /opt/top.txt
```

라벨 매칭:

```bash
k top pod -l app=web --sort-by=memory --no-headers | head -1 | awk '{print $1}'
```

### 패턴 6: 비정상 Pod 디버깅

"CrashLoopBackOff 상태의 Pod이 있다. 원인을 찾아 고쳐라."

진단 흐름:

```bash
k get pod                              # STATUS 확인
k describe pod my-pod                  # Events, Last State, Exit Code 확인
k logs my-pod --previous               # 크래시 전 로그
k logs my-pod -c <container> --previous
```

흔한 원인과 해결:

- `ImagePullBackOff` → 이미지 이름/태그 오타 → `k edit` 또는 `k set image`
- `CrashLoopBackOff` + 로그에 명령 에러 → command/args 잘못 → `k edit`
- `OOMKilled` → memory limit 부족 → resources 늘리기
- `Pending` → 자원 부족 / nodeSelector 미스 → `describe` Events 확인

## 함정 포인트

### 함정 1 — initialDelaySeconds 너무 짧음

```yaml
livenessProbe:
  initialDelaySeconds: 0    # ❌ 앱 시작 전에 체크 → 재시작 루프
```

앱이 5초 후에 listen 시작하는데 probe가 즉시 체크하면 실패 → 재시작 → 또 실패 → 무한 루프. 앱 시작 시간보다 충분히 길게 설정.

### 함정 2 — Liveness만 설정, Readiness 누락

Liveness만 있고 readiness가 없으면, 앱이 워밍업 중에도 Service가 트래픽을 보냅니다. 사용자가 500 에러를 받는 시간이 생김.

### 함정 3 — Readiness Probe로 데드락 감지 시도

Readiness 실패는 endpoint에서만 제거할 뿐, Pod을 재시작하지 않습니다. 데드락은 **liveness**로 감지해야 함.

### 함정 4 — `failureThreshold` 1로 설정

```yaml
failureThreshold: 1   # ❌ 한 번 실패하면 즉시 재시작 → 일시적 부하에 취약
```

기본값 3을 그대로 두는 게 안전. 시험에서 명시적으로 1을 요구하면 그대로.

### 함정 5 — `k logs my-pod` 만으로는 크래시 원인 못 봄

```bash
k logs my-pod              # ❌ 현재(재시작 후) 로그만
k logs my-pod --previous   # ✅ 크래시한 인스턴스의 로그
```

CrashLoopBackOff 디버깅의 핵심은 `--previous`.

### 함정 6 — Multi-container Pod에서 `-c` 누락

```bash
k logs my-pod        # ❌ multi-container면 에러
k logs my-pod -c app # ✅
```

에러 메시지에 컨테이너 목록이 나오니 그걸 보고 다시 시도.

### 함정 7 — `kubectl top` 실패

```
error: Metrics API not available
```

metrics-server가 설치 안 됨. CKAD 시험 환경에서는 보통 설치되어 있지만, 만약 안 된다면 문제 자체가 metrics를 안 묻는 것일 가능성. 우회 방법:

```bash
# Pod 안에서 직접 확인
k exec my-pod -- top -bn1
k exec my-pod -- cat /sys/fs/cgroup/memory/memory.usage_in_bytes
```

### 함정 8 — Events는 기본 1시간 후 삭제

문제 발생 후 시간이 오래 지났으면 events에서 정보를 못 찾을 수 있음. `describe pod`의 Events 섹션도 동일. 빨리 확인.

### 함정 9 — `successThreshold` 제한

```yaml
livenessProbe:
  successThreshold: 2   # ❌ liveness는 반드시 1
```

Liveness와 Startup의 `successThreshold`는 반드시 1. Readiness만 2 이상 가능.

### 함정 10 — Probe 동작 검증 누락

Probe를 추가하고 끝내면 안 됩니다. 적용 후 동작 확인:

```bash
k get pod my-pod
# RESTARTS 컬럼 증가 안 함 → 정상
# RESTARTS 컬럼이 계속 증가 → liveness 실패 중

k describe pod my-pod | grep -A 5 Liveness
k describe pod my-pod | grep -A 10 Events  # probe 실패 이벤트 확인
```

## 디버깅 흐름 (시험 표준 프로세스)

문제 발생 시 따라가는 표준 순서:

```bash
# 1. 상태 확인
k get pod                              # STATUS, READY, RESTARTS
k get pod my-pod -o wide               # 노드, IP

# 2. 상세 + 이벤트
k describe pod my-pod                  # Events 섹션 필독

# 3. 로그
k logs my-pod                          # 현재
k logs my-pod --previous               # 크래시 전 (CrashLoop 시 핵심)
k logs my-pod -c <container>           # multi-container

# 4. 안에 들어가서 확인
k exec -it my-pod -- sh
k exec -it my-pod -c <container> -- sh

# 5. 메트릭
k top pod my-pod --containers          # OOMKilled 의심 시

# 6. 클러스터 이벤트
k get events --sort-by=.metadata.creationTimestamp | tail -20
```
