### 시작 세팅

bash

```bash
alias k=kubectl
export do="--dry-run=client -o yaml"
export now="--grace-period=0 --force"
```

### 자주 쓰는 YAML 생성 명령

bash

```bash
# ServiceAccount
k create sa my-sa $do > sa.yaml
k create sa my-sa -n dev $do > sa.yaml

# Role / RoleBinding
k create role pod-reader --verb=get,list,watch --resource=pods $do > role.yaml
k create rolebinding pod-reader-rb --role=pod-reader --serviceaccount=dev:my-sa -n dev $do > rb.yaml

# ClusterRole / ClusterRoleBinding
k create clusterrole node-reader --verb=get,list --resource=nodes $do > cr.yaml
k create clusterrolebinding node-reader-crb --clusterrole=node-reader --serviceaccount=dev:my-sa $do > crb.yaml

# Secret
k create secret generic db-secret --from-literal=password=s3cr3t $do > secret.yaml
k create secret tls my-tls --cert=server.crt --key=server.key $do > tls.yaml

# Token (1.24+)
k create token my-sa
```

### 권한 검증 명령 (반드시 외울 것)

bash

```bash
# 핵심 패턴: --as=system:serviceaccount:<namespace>:<sa-name>
k auth can-i get pods --as=system:serviceaccount:dev:my-sa -n dev
k auth can-i create deployments --as=system:serviceaccount:dev:my-sa
k auth can-i "*" "*" --as=system:serviceaccount:dev:my-sa

# 본인 권한 확인
k auth can-i get pods
```

### explain으로 확인할 필드 (외우기 어려운 것들)

bash

```bash
k explain pod.spec.securityContext
k explain pod.spec.containers.securityContext
k explain pod.spec.containers.securityContext.capabilities
k explain networkpolicy.spec --recursive | less
k explain role.rules
```

### 출제 패턴

크게 세 가지 유형으로 정형화되어 있습니다.

**유형 1: SA + RBAC + 검증** (가장 자주 출제) "SA 생성 → Role/RoleBinding 생성 → Pod에 SA 할당 → auth can-i로 검증" 한 세트로 묶여 나옵니다. namespace를 빠뜨리지 않는 게 중요합니다.

**유형 2: SecurityContext 설정** "Pod를 UID 1000으로 실행하고 capability NET_ADMIN 추가, privilege escalation 금지" 같은 식. Pod 레벨과 Container 레벨 중 어디에 설정할지 문제 지시를 정확히 읽어야 합니다. **Container 레벨이 Pod 레벨을 덮어씁니다.**

**유형 3: NetworkPolicy** "frontend Pod만 backend의 80 포트로 접근 가능, 그 외 모두 차단." 가장 까다로운 유형입니다.

### NetworkPolicy 함정 포인트 (시험 직전 반드시 복습)

**함정 1 — dash 위치에 따른 AND/OR**

yaml

```yaml
# OR: frontend Pod 이거나, prod namespace의 모든 Pod
- from:
  - podSelector:
      matchLabels:
        app: frontend
  - namespaceSelector:
      matchLabels:
        env: prod

# AND: prod namespace의 frontend Pod만
- from:
  - namespaceSelector:
      matchLabels:
        env: prod
    podSelector:
      matchLabels:
        app: frontend
```

dash가 두 개 → OR, dash 하나에 두 selector → AND. 이 차이를 자주 물어봅니다.

**함정 2 — policyTypes 누락** `policyTypes`에 `Egress`를 안 적으면 egress 규칙은 무시됩니다. 명시적으로 둘 다 적어야 합니다.

**함정 3 — DNS 허용** Egress를 잠그면 DNS(UDP 53)도 막혀서 Pod이 통신을 못 합니다. egress 정책엔 kube-system의 DNS 허용을 추가하는 함정이 자주 있습니다.

yaml

```yaml
- to:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: kube-system
  ports:
  - protocol: UDP
    port: 53
```

### 빠르게 작성하는 팁

- ServiceAccount, Role, RoleBinding은 `kubectl create`로 거의 다 생성 가능. YAML 손으로 안 쓰는 게 답.
- SecurityContext와 NetworkPolicy는 imperative 명령어가 없으니 `explain --recursive`로 필드 확인하면서 작성.
- Pod에 SA 할당은 `spec.serviceAccountName` 한 줄 추가만 하면 됨.
