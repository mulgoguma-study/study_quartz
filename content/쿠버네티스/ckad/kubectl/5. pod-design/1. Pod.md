
# Pod 완벽 정리

Pod은 Kubernetes의 가장 기본 단위입니다. CKAD에서는 단독 Pod 문제뿐 아니라 Deployment, Job, CronJob 등 거의 모든 문제에 Pod 스펙이 포함되어 있어서, Pod 스펙을 빠르고 정확히 작성하는 능력이 시험 전체 점수를 좌우합니다.

## 1. Pod의 기본 구조

Pod은 하나 이상의 컨테이너를 묶은 단위로, 같은 Pod 안의 컨테이너들은 **네트워크와 볼륨을 공유**합니다.

```
Pod
 ├── Container 1 (메인)
 ├── Container 2 (사이드카)
 ├── 공유 네트워크 (같은 localhost)
 └── 공유 볼륨
```

같은 Pod 안의 컨테이너끼리는 `localhost`로 통신합니다. 다른 Pod끼리는 Service나 Pod IP로 통신.

## 2. Pod YAML 전체 구조

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: default
  labels:
    app: web
    tier: front
  annotations:
    description: "main web pod"
spec:
  restartPolicy: Always         # Always(기본) / OnFailure / Never
  serviceAccountName: my-sa
  nodeSelector:
    disktype: ssd
  containers:
  - name: app
    image: nginx:1.25
    imagePullPolicy: IfNotPresent  # Always / IfNotPresent / Never
    ports:
    - containerPort: 80
      name: http
    command: ["nginx"]
    args: ["-g", "daemon off;"]
    env:
    - name: ENV
      value: prod
    resources:
      requests:
        cpu: "100m"
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
    volumeMounts:
    - name: data
      mountPath: /data
    livenessProbe:
      httpGet:
        path: /healthz
        port: 80
      initialDelaySeconds: 10
      periodSeconds: 5
    readinessProbe:
      httpGet:
        path: /ready
        port: 80
  volumes:
  - name: data
    emptyDir: {}
```

## 3. Pod 생성

### 명령어로 생성 (가장 빠른 방법)

```bash
# 기본 생성
k run nginx --image=nginx

# YAML로 출력만 (수정용 골격)
k run nginx --image=nginx $do > pod.yaml

# 포트 지정
k run nginx --image=nginx --port=80 $do > pod.yaml

# 환경변수 지정
k run nginx --image=nginx --env="ENV=prod" --env="LOG=debug" $do > pod.yaml

# 라벨 지정
k run nginx --image=nginx --labels="app=web,tier=front" $do > pod.yaml

# 명령어 지정 (-- 뒤에 args)
k run busybox --image=busybox $do -- sleep 3600 > pod.yaml

# command와 args 모두
k run busybox --image=busybox --command $do -- /bin/sh -c "sleep 3600" > pod.yaml

# 즉시 실행 + 자동 삭제 (디버깅용)
k run tmp --image=busybox --rm -it --restart=Never -- sh

# DNS 테스트용
k run dns-test --image=busybox --rm -it --restart=Never -- nslookup kubernetes
```

`$do`는 `--dry-run=client -o yaml`의 alias입니다.

### `kubectl run` 옵션 정리

|옵션|설명|
|---|---|
|`--image`|이미지 (필수)|
|`--port`|containerPort|
|`--env`|환경변수 (여러 번 사용 가능)|
|`--labels`|라벨 (콤마 구분)|
|`--restart=Never`|Pod (기본은 Pod 단독 생성)|
|`--rm`|종료 후 자동 삭제|
|`-it`|인터랙티브 모드|
|`--command`|뒤의 `--` 이후를 command로 (없으면 args)|
|`-- <명령>`|command 또는 args|

## 4. Multi-container Pod

같은 Pod 안에 여러 컨테이너를 두는 패턴입니다. 명령어로는 안 되니 **YAML 직접 작성** 필요.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: multi
spec:
  containers:
  - name: main
    image: nginx
    volumeMounts:
    - name: shared
      mountPath: /usr/share/nginx/html
  - name: sidecar
    image: busybox
    command: ["sh", "-c", "while true; do echo $(date) > /data/index.html; sleep 5; done"]
    volumeMounts:
    - name: shared
      mountPath: /data
  volumes:
  - name: shared
    emptyDir: {}
```

**3가지 패턴**:

- **Sidecar**: 메인을 보조 (로그 수집, 동적 콘텐츠 생성)
- **Adapter**: 메인의 출력을 변환
- **Ambassador**: 메인 대신 외부 통신 담당

CKAD에서는 패턴 이름보다 **"두 컨테이너가 같은 볼륨을 공유한다"** 같은 실제 구성을 묻습니다.

## 5. Init Container

메인 컨테이너 시작 **전에** 실행되어 완료되어야 하는 컨테이너. 순차 실행되며, 모두 성공해야 메인이 시작됩니다.

```yaml
spec:
  initContainers:
  - name: init-db
    image: busybox
    command: ["sh", "-c", "until nslookup db; do sleep 2; done"]
  - name: init-config
    image: busybox
    command: ["sh", "-c", "echo 'ready' > /config/status"]
    volumeMounts:
    - name: config
      mountPath: /config
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: config
      mountPath: /etc/config
  volumes:
  - name: config
    emptyDir: {}
```

**용도**: 의존 서비스 대기, 설정 파일 준비, 데이터 다운로드 등.

## 6. 컨테이너 명령어 (command / args)

Docker의 ENTRYPOINT/CMD에 대응합니다.

|Kubernetes|Docker|의미|
|---|---|---|
|`command`|ENTRYPOINT|실행할 명령|
|`args`|CMD|명령의 인자|

```yaml
containers:
- name: app
  image: busybox
  command: ["sh", "-c"]
  args: ["echo hello && sleep 3600"]
```

또는 한 줄로:

```yaml
command: ["sh", "-c", "echo hello && sleep 3600"]
```

**함정**: `command`를 지정하면 이미지의 ENTRYPOINT가 무시됩니다. 이미지가 의도한 동작이 안 될 수 있으니 주의.

## 8. Resources (requests / limits)

```yaml
resources:
  requests:        # 보장받는 최소 자원 (스케줄링 기준)
    cpu: "100m"     # 0.1 core
    memory: "128Mi"
  limits:          # 최대 사용 가능 (초과 시 throttle/kill)
    cpu: "500m"
    memory: "512Mi"
```

**단위**:

- CPU: `1` = 1 core, `500m` = 0.5 core, `100m` = 0.1 core
- 메모리: `Mi` (메비바이트), `Gi` (기비바이트). `M`/`G`(10진수)와 다름

**동작**:

- `requests`만큼 자원이 있는 노드에 스케줄링
- CPU `limits` 초과: throttle (속도 제한)
- 메모리 `limits` 초과: OOMKilled (강제 종료)

명령어로 설정:

```bash
k set resources pod my-pod --limits=cpu=500m,memory=512Mi --requests=cpu=100m,memory=128Mi
```

## 9. Probes (Liveness / Readiness / Startup)

### Liveness Probe

컨테이너가 살아 있는지 확인. 실패 시 컨테이너 재시작.

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 80
  initialDelaySeconds: 10   # 첫 체크까지 대기
  periodSeconds: 5          # 체크 주기
  timeoutSeconds: 1         # 응답 대기 시간
  failureThreshold: 3       # 연속 실패 허용 횟수
  successThreshold: 1
```

### Readiness Probe

트래픽 받을 준비가 됐는지 확인. 실패 시 Service의 endpoint에서 제거 (Pod은 살아있음).

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 80
  initialDelaySeconds: 5
  periodSeconds: 3
```

### Startup Probe

초기 시작이 오래 걸리는 앱용. 성공할 때까지 다른 probe 비활성화.

```yaml
startupProbe:
  httpGet:
    path: /started
    port: 80
  failureThreshold: 30
  periodSeconds: 10
```

### Probe 종류 (3가지 방식)

```yaml
# HTTP
httpGet:
  path: /healthz
  port: 80

# TCP
tcpSocket:
  port: 80

# 명령 실행
exec:
  command: ["cat", "/tmp/healthy"]
```

**차이 요약**:

|Probe|실패 시|용도|
|---|---|---|
|Liveness|컨테이너 재시작|데드락 감지|
|Readiness|트래픽 차단|일시적으로 바쁠 때|
|Startup|시작 대기 연장|느린 초기화|

## 10. restartPolicy

|값|의미|사용 가능|
|---|---|---|
|`Always`|항상 재시작 (기본)|Pod, Deployment|
|`OnFailure`|실패 시만 재시작|Pod, Job, CronJob|
|`Never`|재시작 안 함|Pod, Job, CronJob|

**함정**: Job/CronJob은 `Always` 사용 불가. Deployment는 `Always`만 가능.

## 11. Volumes (Pod 레벨)

### emptyDir (Pod 생명주기와 동일)

```yaml
volumes:
- name: cache
  emptyDir: {}

# 메모리 기반 (tmpfs)
- name: mem-cache
  emptyDir:
    medium: Memory
    sizeLimit: 128Mi
```

### hostPath (노드의 디렉토리)

```yaml
volumes:
- name: data
  hostPath:
    path: /data
    type: DirectoryOrCreate
```

### ConfigMap / Secret 마운트

```yaml
volumes:
- name: config
  configMap:
    name: app-config
- name: secret
  secret:
    secretName: db-secret
    defaultMode: 0400      # 권한
```

### PVC 마운트

```yaml
volumes:
- name: data
  persistentVolumeClaim:
    claimName: my-pvc
```

### volumeMounts (컨테이너 레벨)

```yaml
containers:
- name: app
  image: nginx
  volumeMounts:
  - name: config         # volumes의 name과 일치
    mountPath: /etc/config
    readOnly: true
  - name: data
    mountPath: /data
    subPath: app/data    # 볼륨의 특정 하위경로만
```

## 12. nodeSelector / nodeName / affinity

### nodeSelector (단순)

```yaml
spec:
  nodeSelector:
    disktype: ssd
```

먼저 노드에 라벨을 붙입니다:

```bash
k label node worker-1 disktype=ssd
```

### nodeName (직접 지정, 강제)

```yaml
spec:
  nodeName: worker-1
```

스케줄러를 거치지 않고 강제로 해당 노드에 배치. 시험에 거의 안 나옴.

### Affinity (복잡한 조건)

CKAD에서는 가끔 출제됩니다.

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In
            values: ["ssd", "nvme"]
```

`required` = 반드시, `preferred` = 가능하면.

## 13. Tolerations / Taints

노드에 taint가 있으면 toleration이 있는 Pod만 스케줄링됩니다.

```bash
# 노드에 taint 추가
k taint node worker-1 key=value:NoSchedule

# taint 제거
k taint node worker-1 key-
```

```yaml
spec:
  tolerations:
  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"
```

`effect`: `NoSchedule`, `PreferNoSchedule`, `NoExecute`.

CKA에서 더 자주 나오지만 CKAD에서도 가끔 출제됩니다.

## 14. Pod 상태 (Phase / Conditions)

```bash
k get pod
# NAME      READY   STATUS    RESTARTS   AGE
# my-pod    1/1     Running   0          5m
```

**Phase 값**:

- `Pending`: 스케줄링 대기 또는 이미지 pull 중
- `Running`: 노드에 할당되고 컨테이너 실행 중
- `Succeeded`: 모든 컨테이너 정상 종료 (Job용)
- `Failed`: 컨테이너가 비정상 종료
- `Unknown`: 노드와 통신 불가

**자주 보는 STATUS (Phase는 아님)**:

- `ContainerCreating`: 컨테이너 생성 중
- `ImagePullBackOff`: 이미지 pull 실패
- `CrashLoopBackOff`: 반복 크래시
- `Error`: 에러로 종료
- `Completed`: Job의 정상 종료
- `OOMKilled`: 메모리 초과로 종료
- `Terminating`: 삭제 중

## 15. 디버깅 명령

```bash
# 기본 정보
k get pod                          # 목록
k get pod -o wide                  # 노드 IP 포함
k get pod my-pod -o yaml           # 전체 YAML
k describe pod my-pod              # 상세 + 이벤트

# 로그
k logs my-pod                      # 단일 컨테이너
k logs my-pod -c sidecar           # 특정 컨테이너
k logs my-pod --previous           # 이전(크래시 전) 로그
k logs my-pod -f                   # 실시간 (follow)
k logs my-pod --tail=50            # 마지막 50줄
k logs my-pod --since=10m          # 10분 이내
k logs my-pod --all-containers     # 모든 컨테이너

# 컨테이너 내부 접속
k exec my-pod -- ls /app           # 단발 명령
k exec -it my-pod -- sh            # 대화형
k exec -it my-pod -c sidecar -- sh # 특정 컨테이너

# 파일 복사
k cp my-pod:/etc/config.yaml ./config.yaml
k cp ./local.txt my-pod:/tmp/local.txt
k cp my-pod:/log/app.log ./app.log -c sidecar

# Port forwarding (외부에서 Pod에 접근)
k port-forward pod/my-pod 8080:80

# 이벤트
k get events --sort-by=.metadata.creationTimestamp
k get events --field-selector involvedObject.name=my-pod

# 리소스 사용량 (metrics-server 필요)
k top pod
k top pod my-pod --containers
```

## 16. 출제 패턴

Pod은 단독 문제뿐 아니라 다른 영역의 빌딩블록으로도 자주 등장합니다.

### 패턴 1: 기본 Pod 생성 + 명령어/환경변수

"busybox 이미지로 Pod을 만들고, 명령어로 `sleep 3600`을 실행하라."

```bash
k run busybox --image=busybox $do -- sleep 3600 > pod.yaml
k apply -f pod.yaml
```

### 패턴 2: Multi-container Pod

"두 컨테이너가 같은 emptyDir을 공유하게 하라."

YAML 직접 작성. `volumeMounts`의 name이 `volumes`의 name과 일치하는지 항상 확인.

### 패턴 3: Init Container

"메인 컨테이너 시작 전에 nslookup으로 특정 서비스가 준비됐는지 확인하는 init container를 추가하라."

```yaml
spec:
  initContainers:
  - name: wait-for-svc
    image: busybox
    command: ["sh", "-c", "until nslookup my-svc; do sleep 2; done"]
```

### 패턴 4: Probe 설정

"HTTP /healthz로 liveness probe, /ready로 readiness probe를 설정하라."

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 80
  initialDelaySeconds: 10
  periodSeconds: 5
readinessProbe:
  httpGet:
    path: /ready
    port: 80
```

### 패턴 5: Resources 설정

"requests cpu=100m memory=128Mi, limits cpu=500m memory=512Mi로 설정하라."

명령어 또는 YAML 직접.

### 패턴 6: Env / ConfigMap / Secret 연결

"db-secret의 password 키 값을 DB_PASSWORD 환경변수로 주입하라."

```yaml
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: password
```

### 패턴 7: nodeSelector

"disktype=ssd 라벨이 붙은 노드에만 Pod이 스케줄링되게 하라."

```bash
k label node worker-1 disktype=ssd
```

```yaml
spec:
  nodeSelector:
    disktype: ssd
```

### 패턴 8: 디버깅 문제

"Pod이 ImagePullBackOff 상태다. 원인을 찾아 해결하라."

```bash
k describe pod my-pod          # Events 확인
k get pod my-pod -o yaml | grep image:
# 이미지 오타 발견 → 수정
```

## 17. 함정 포인트

### 함정 1 — restartPolicy 기본값

```yaml
# 명시 안 하면 Always
spec:
  containers: ...
```

Job/CronJob 안에서는 반드시 `Never` 또는 `OnFailure` 지정.

### 함정 2 — `kubectl run` 동작 변경

이전 버전에서는 `k run`이 Deployment를 만들기도 했지만, **현재는 Pod만 생성**합니다. 시험 버전(1.30+)에서는 Pod이 기본.

### 함정 3 — command vs args 혼동

```yaml
# 잘못된 예
command: ["sleep 3600"]      # ❌ 한 문자열로 인식 → 에러

# 올바른 예
command: ["sleep", "3600"]   # ✅ 배열로 분리
# 또는
command: ["sh", "-c", "sleep 3600"]   # ✅ shell로 실행
```

### 함정 4 — volumeMount의 name 불일치

```yaml
containers:
- volumeMounts:
  - name: data         # 이거와
    mountPath: /data
volumes:
- name: datavol        # 다르면 Pod 생성 실패
  emptyDir: {}
```

### 함정 5 — Pod은 immutable한 필드가 많음

- `spec.containers[*].image` 외에는 거의 변경 불가
- 변경하려면 Pod을 삭제하고 재생성 필요
- 이미지만 바꿀 때는 `k set image pod/my-pod nginx=nginx:1.25` 가능

### 함정 6 — initialDelaySeconds 누락

Probe에서 `initialDelaySeconds`가 없거나 너무 짧으면, 앱이 미처 시작하기 전에 liveness가 실패해서 무한 재시작 루프에 빠집니다. 시작이 느린 앱이면 5~30초 정도 여유.

### 함정 7 — Resources 단위 헷갈림

```yaml
memory: 128M     # 128,000,000 bytes (10진수)
memory: 128Mi    # 128 * 1024 * 1024 bytes (2진수) ← 일반적
```

시험에서는 거의 항상 `Mi`, `Gi` 단위로 출제됩니다.

### 함정 8 — Pod 삭제가 느림

```bash
k delete pod my-pod              # 기본 30초 graceful
k delete pod my-pod --grace-period=0 --force   # 즉시 (= $now)
```

시험에서 시간 절약하려면 `$now` alias 활용.

### 함정 9 — Pod이 종료되면 다시 안 살아남

restartPolicy가 Never/OnFailure인 Pod은 종료 후 자동 재생성되지 않습니다. Deployment처럼 자동 복구를 원하면 상위 리소스 필요.

### 함정 10 — 이미지 태그 생략 → latest

```yaml
image: nginx     # → nginx:latest 자동 적용
```

`imagePullPolicy`도 `latest`면 `Always`, 명시적 태그면 `IfNotPresent`가 기본.

## 18. 빠르게 작성하는 팁

- **Pod 골격은 항상 `k run ... $do`로 생성**. 직접 YAML 쓰지 말 것.
- **Multi-container와 init container는 YAML 직접 작성**. 명령어로 안 됨. 첫 컨테이너는 `k run`으로 만들고, 두 번째부터 `containers:` 배열에 추가.
- **`k explain --recursive`로 필드 빠르게 확인**:
    
    ```bash
    k explain pod.spec.containers.lifecycle --recursivek explain pod.spec.affinity --recursive | less
    ```
    
- **이미지 변경은 명령어로**: `k set image pod/my-pod app=nginx:1.25`. 단, Pod은 image만 mutable.
- **디버깅은 `describe` → `logs` → `events` 순서**가 기본. 이 흐름을 외워두면 문제 발생 시 1분 안에 원인 파악 가능.
- **임시 디버깅 Pod 만들기**:
    
    ```bash
    k run debug --image=busybox --rm -it --restart=Never -- shk run curl --image=curlimages/curl --rm -it --restart=Never -- sh
    ```
    
    네트워크 테스트, DNS 확인 등에 매우 유용.
- **`kubectl edit pod`은 거의 안 됨**. 대부분의 필드가 immutable이라 에러. Pod을 삭제하고 재생성하는 게 빠름.
- **라벨/어노테이션은 항상 명령어로**:
    
    ```bash
    k label pod my-pod env=prodk annotate pod my-pod owner="team-A"
    ```
