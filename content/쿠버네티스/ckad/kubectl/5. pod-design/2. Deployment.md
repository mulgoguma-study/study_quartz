# Deployment 완벽 정리

Deployment는 CKAD에서 가장 자주 다루는 리소스입니다. ReplicaSet을 통해 Pod을 관리하면서, 무중단 배포(Rolling Update)와 롤백을 자동화해주는 것이 핵심 역할입니다.

## 1. Deployment의 구조

Deployment는 직접 Pod을 만들지 않습니다. **Deployment → ReplicaSet → Pod** 계층 구조로 동작합니다.

```
Deployment (배포 전략 관리)
    └── ReplicaSet (특정 버전의 Pod 묶음)
            └── Pod (실제 컨테이너)
```

이미지를 바꾸면 새 ReplicaSet이 생성되고, 기존 ReplicaSet은 0으로 줄어들면서 점진적으로 교체됩니다. 롤백은 이 과거 ReplicaSet을 다시 살리는 방식입니다.

```bash
k get deploy,rs,pod -l app=web
# NAME                          READY   UP-TO-DATE   AVAILABLE
# deployment.apps/web            3/3     3            3

# NAME                                    DESIRED   CURRENT   READY
# replicaset.apps/web-7d9c8b5f8b          3         3         3       # 현재
# replicaset.apps/web-6c8b9d7f5a          0         0         0       # 이전 버전
```

## 2. Deployment YAML 전체 구조

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 3                          # Pod 개수
  revisionHistoryLimit: 10             # 보관할 이전 ReplicaSet 개수 (기본 10)
  progressDeadlineSeconds: 600         # 배포 진행 제한 시간
  minReadySeconds: 0                   # Pod이 Ready 후 최소 대기 시간
  strategy:                            # 배포 전략
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                      # 추가로 생성 가능한 Pod 수
      maxUnavailable: 0                # 동시에 사용 불가능한 Pod 수
  selector:                            # 어떤 Pod을 관리할지 (immutable)
    matchLabels:
      app: web
  template:                            # Pod 템플릿
    metadata:
      labels:
        app: web                       # selector와 반드시 일치
    spec:
      containers:
      - name: nginx
        image: nginx:1.24
        ports:
        - containerPort: 80
```

각 필드의 의미:

- `replicas`: 유지할 Pod 개수
- `selector.matchLabels`: 이 Deployment가 관리할 Pod의 라벨. **생성 후 변경 불가**
- `template.metadata.labels`: Pod이 가질 라벨. selector와 반드시 일치
- `strategy`: 배포 방식 (RollingUpdate 또는 Recreate)
- `revisionHistoryLimit`: 롤백 가능한 이전 버전 개수

## 3. Deployment 생성

### 명령어로 생성 (권장)

```bash
# 기본
k create deploy web --image=nginx

# replica 지정
k create deploy web --image=nginx --replicas=3

# 포트 지정
k create deploy web --image=nginx --port=80

# YAML로 출력 (수정 후 적용용)
k create deploy web --image=nginx --replicas=3 --port=80 $do > deploy.yaml
```

CKAD에서는 `k create deploy`로 기본 골격을 만들고 필요한 필드만 추가하는 패턴이 가장 빠릅니다.

### 명령어로 안 되는 필드 (YAML 수정 필요)

- `strategy` (RollingUpdate / Recreate)
- `maxSurge`, `maxUnavailable`
- 여러 컨테이너 (multi-container)
- 환경변수, volume, securityContext
- nodeSelector, affinity, tolerations
- resources (requests/limits)

이런 필드는 `$do`로 YAML 생성 후 직접 추가합니다.

## 4. 배포 전략 (Strategy)

### RollingUpdate (기본값)

점진적으로 Pod을 교체합니다. 무중단 배포가 가능한 기본 전략입니다.

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1            # 목표 replica 외에 추가로 1개 더 만들 수 있음
      maxUnavailable: 0      # 동시에 사용 불가능한 Pod 0개 (무중단)
```

**maxSurge / maxUnavailable의 의미** (replicas=3 기준):

|maxSurge|maxUnavailable|동시 가동 Pod 범위|특징|
|---|---|---|---|
|1|0|3~4|무중단, 점진적|
|0|1|2~3|자원 절약, 잠시 다운 가능|
|25%|25%|기본값|균형|
|100%|0|3~6|빠른 배포, 자원 2배 필요|

값은 **숫자 또는 퍼센트 문자열** 둘 다 가능:

```yaml
maxSurge: 2          # 숫자
maxSurge: "50%"      # 퍼센트는 반드시 큰따옴표
```

### Recreate

모든 Pod을 한 번에 죽이고 새로 만듭니다. 다운타임이 발생하지만 자원을 두 배로 쓰지 않습니다.

```yaml
spec:
  strategy:
    type: Recreate
    # rollingUpdate 필드는 쓰지 않음
```

데이터베이스처럼 동시에 두 버전이 떠 있으면 안 되는 경우에 사용. CKAD에서는 가끔 출제됩니다.

## 5. 이미지 업데이트

### set image (가장 흔한 방식)

```bash
# 단일 컨테이너
k set image deploy/web nginx=nginx:1.25

# 다중 컨테이너 (컨테이너명 정확히 지정)
k set image deploy/web nginx=nginx:1.25 sidecar=busybox:1.36

# 모든 Deployment의 특정 컨테이너 한번에
k set image deploy --all nginx=nginx:1.25
```

문법: `<container-name>=<new-image>`. 컨테이너 이름이 헷갈리면:

```bash
k get deploy web -o jsonpath='{.spec.template.spec.containers[*].name}'
```

### edit

```bash
k edit deploy web
```

에디터에서 직접 수정. `image:` 필드를 찾아서 바꾸면 됩니다. 환경변수나 다른 필드도 같이 바꿀 때 유용.

### apply

YAML 파일을 수정한 뒤:

```bash
k apply -f deploy.yaml
```

## 6. Rollout 관리

### 진행 상태 확인

```bash
# 현재 배포 진행 상태 (완료될 때까지 대기)
k rollout status deploy/web

# 진행 안 됐다면 한 번 더 확인
k get deploy web
k describe deploy web
```

`rollout status`는 배포가 완료되면 종료됩니다. 시험에서 다음 문제로 넘어가기 전에 반드시 확인하는 습관을 들이세요.

### 히스토리 확인

```bash
# 전체 revision 목록
k rollout history deploy/web

# REVISION  CHANGE-CAUSE
# 1         <none>
# 2         <none>
# 3         <none>

# 특정 revision 상세 (어떤 이미지였는지 확인)
k rollout history deploy/web --revision=2
```

`CHANGE-CAUSE`는 `--record` deprecated 이후로 거의 비어 있습니다. 필요하면 annotation으로 직접 추가:

```bash
k annotate deploy/web kubernetes.io/change-cause="image updated to 1.25"
```

### 롤백

```bash
# 바로 직전 버전으로 롤백
k rollout undo deploy/web

# 특정 revision으로 롤백
k rollout undo deploy/web --to-revision=2
```

롤백하면 새 revision 번호가 부여됩니다(원래 revision으로 가는 게 아니라, 그 내용을 가진 새 revision이 생성).

### 일시정지 / 재개

```bash
# 일시정지 (여러 변경사항을 묶어서 배포할 때)
k rollout pause deploy/web

# 이 상태에서 여러 변경
k set image deploy/web nginx=nginx:1.25
k set env deploy/web ENV=prod

# 한 번에 적용
k rollout resume deploy/web
```

### 강제 재시작

```bash
# 이미지 변경 없이 Pod 재생성 (Secret/ConfigMap 변경 반영 등)
k rollout restart deploy/web
```

새 ReplicaSet이 생성되며 무중단으로 모든 Pod이 교체됩니다.

## 7. Scaling

```bash
# 직접 스케일
k scale deploy web --replicas=5

# 조건부 스케일 (현재 replica가 3일 때만 5로)
k scale deploy web --current-replicas=3 --replicas=5

# 여러 Deployment 한 번에
k scale deploy web api --replicas=3

# 라벨로 일괄 스케일
k scale deploy -l app=frontend --replicas=2
```

YAML의 `replicas` 필드를 직접 수정해도 되지만, 명령이 빠릅니다.

## 8. 환경변수 / 이미지 / 리소스 설정 (set)

```bash
# 환경변수 추가/변경
k set env deploy/web ENV=prod LOG_LEVEL=debug

# 환경변수 삭제
k set env deploy/web ENV-

# Secret/ConfigMap에서 환경변수 가져오기
k set env deploy/web --from=secret/db-secret
k set env deploy/web --from=configmap/app-config

# 리소스 limits/requests 설정
k set resources deploy/web --limits=cpu=500m,memory=512Mi --requests=cpu=100m,memory=128Mi

# Service Account 변경
k set serviceaccount deploy/web my-sa
```

이런 set 명령들도 모두 새 ReplicaSet을 만들고 rolling update를 트리거합니다.

## 9. 출제 패턴

Deployment는 다음 6가지 패턴이 거의 매 시험 변형되어 나옵니다.

### 패턴 1: 기본 생성 + 스케일

"web Deployment를 nginx 이미지로 만들고, replica를 4로 설정하라."

```bash
k create deploy web --image=nginx --replicas=4
```

### 패턴 2: 이미지 업데이트 + 롤백

"web Deployment의 이미지를 nginx:1.25로 업데이트한 뒤, 이전 버전으로 롤백하라."

```bash
k set image deploy/web nginx=nginx:1.25
k rollout status deploy/web
k rollout undo deploy/web
```

### 패턴 3: Rolling update 전략 설정

"maxSurge=2, maxUnavailable=1로 설정하라."

```bash
k edit deploy web
```

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2
      maxUnavailable: 1
```

### 패턴 4: Recreate 전략으로 변경

"web Deployment의 배포 전략을 Recreate로 변경하라."

```yaml
spec:
  strategy:
    type: Recreate
    # rollingUpdate 블록은 반드시 제거
```

### 패턴 5: 특정 revision으로 롤백

"web Deployment를 revision 2로 롤백하라."

```bash
k rollout history deploy/web                  # revision 목록 확인
k rollout history deploy/web --revision=2     # 내용 확인
k rollout undo deploy/web --to-revision=2
```

### 패턴 6: 환경변수 / 리소스 / 라벨 수정

"web Deployment의 모든 Pod에 ENV=prod 환경변수를 추가하라."

```bash
k set env deploy/web ENV=prod
```

## 10. 함정 포인트

### 함정 1 — selector와 template label 불일치

```yaml
spec:
  selector:
    matchLabels:
      app: web              # 이거와
  template:
    metadata:
      labels:
        app: webserver      # 다르면 생성 실패
```

`kubectl create deploy`로 만들면 자동으로 맞춰지지만, YAML을 직접 작성하거나 수정할 때 자주 실수합니다.

### 함정 2 — selector는 immutable

생성 후에는 `selector.matchLabels`를 변경할 수 없습니다. 바꾸려면 삭제 후 재생성.

```bash
k delete deploy web
k create deploy web --image=nginx
```

### 함정 3 — maxSurge / maxUnavailable 동시 0

```yaml
rollingUpdate:
  maxSurge: 0
  maxUnavailable: 0   # ❌ 배포가 영원히 진행 안 됨
```

둘 중 하나는 반드시 1 이상이어야 합니다. 문제에서 `maxUnavailable: 0`을 요구하면 `maxSurge`는 1 이상 설정.

### 함정 4 — 퍼센트는 문자열

```yaml
maxSurge: 25%       # ❌ YAML 파싱 에러
maxSurge: "25%"     # ✅
```

### 함정 5 — Recreate에서 rollingUpdate 필드 남김

```yaml
spec:
  strategy:
    type: Recreate
    rollingUpdate:        # ❌ Recreate에서는 이 블록이 있으면 에러
      maxSurge: 1
```

전략을 바꿀 때 `rollingUpdate` 블록을 통째로 지워야 합니다.

### 함정 6 — `--record` deprecated

```bash
k set image deploy/web nginx=nginx:1.25 --record   # ❌ deprecated
```

그냥 `set image`만 쓰면 됩니다. CHANGE-CAUSE를 기록하고 싶으면 annotation으로:

```bash
k annotate deploy/web kubernetes.io/change-cause="update to 1.25" --overwrite
```

### 함정 7 — rollout undo 후 revision 번호

```
1 → 2 → 3 → undo → 4
```

revision 2로 undo하면 revision 4가 새로 생기고 내용은 revision 2와 동일합니다. revision 2 자체로 돌아가는 게 아닙니다.

### 함정 8 — Pod을 직접 삭제해도 다시 생김

```bash
k delete pod web-xxx     # ReplicaSet이 즉시 새 Pod 생성
```

Deployment가 관리하는 Pod은 직접 삭제해도 ReplicaSet이 즉시 복구합니다. 진짜 지우려면 Deployment 자체를 삭제.

### 함정 9 — replicas: 0

```bash
k scale deploy web --replicas=0
```

Deployment를 삭제하지 않고 Pod만 모두 없앨 때 유용합니다. 시험에서 "임시로 멈춰라" 같은 변형 문제로 나올 수 있습니다.

### 함정 10 — image pull 실패 시 rollout이 멈춤

이미지가 없거나 오타가 있으면 `rollout status`가 계속 대기합니다.

```bash
k get pods                  # ImagePullBackOff 확인
k describe pod <name>       # 정확한 에러 메시지
k rollout undo deploy/web   # 빠른 복구
```

## 11. 디버깅 명령

```bash
# 전체 상태
k get deploy
k get deploy -o wide
k describe deploy web

# Pod 상태
k get pods -l app=web
k get pods -l app=web -o wide

# ReplicaSet 확인 (Deployment의 하위)
k get rs
k get rs -l app=web

# 어느 ReplicaSet의 Pod인지 확인
k get pod web-xxx -o jsonpath='{.metadata.ownerReferences[0].name}'

# 진행 중인 rollout 확인
k rollout status deploy/web
k rollout history deploy/web

# 이벤트 확인 (문제 발생 시)
k get events --sort-by=.metadata.creationTimestamp
k describe deploy web | tail -30

# 현재 사용 중인 이미지 확인
k get deploy web -o jsonpath='{.spec.template.spec.containers[*].image}'

# Pod의 로그
k logs deploy/web                # 첫 번째 컨테이너
k logs deploy/web -c sidecar     # 특정 컨테이너
k logs deploy/web --all-containers
```

## 12. 빠르게 작성하는 팁

- **Deployment는 99% imperative 명령으로 시작**. `k create deploy ... $do > deploy.yaml`로 골격을 만들고 필요한 필드만 추가.
- **이미지 변경, scale, env 설정은 무조건 명령어로**. YAML 편집은 시간 낭비.
- **`kubectl edit`은 즉시 적용**되니 immutable 필드(selector 등)가 아니면 빠른 수정에 매우 유용.
- **`rollout status`는 채점 전 마지막 확인 도구**. Deployment 문제 풀고 다음 문제로 넘어가기 전 반드시 실행.
- **strategy 관련 문제는 항상 YAML 수정**. 명령어로 안 됨. `k edit deploy/web` 후 strategy 블록 추가.
- **scale을 0으로 했다가 다시 늘리는 것**도 Pod 재생성 효과가 있음. `rollout restart`보다 강력한 리셋.
- **여러 변경을 묶어서 배포**할 때는 `rollout pause` → 변경들 → `rollout resume` 패턴. 시험에는 잘 안 나오지만 알아두면 좋음.
- **ReplicaSet 직접 조작은 거의 안 함**. Deployment가 ReplicaSet을 관리하니 항상 Deployment 레벨에서 명령.

## 13. 자주 헷갈리는 명령 비교

|명령|효과|새 ReplicaSet 생성?|
|---|---|---|
|`k scale deploy/web --replicas=5`|Pod 개수만 변경|❌|
|`k set image deploy/web nginx=nginx:1.25`|이미지 변경|✅|
|`k set env deploy/web ENV=prod`|환경변수 변경|✅|
|`k rollout restart deploy/web`|강제 Pod 재생성|✅|
|`k rollout undo deploy/web`|이전 버전으로|✅ (이전 RS 부활)|
|`k delete pod web-xxx`|해당 Pod만 삭제|❌ (RS가 즉시 복구)|
|`k edit deploy/web`|임의 필드 수정|필드에 따라 다름|

`spec.template` 안의 필드를 바꾸는 작업은 모두 새 ReplicaSet을 만들고 rolling update를 트리거합니다. `replicas`만 바꾸는 건 그렇지 않습니다.

---

Deployment는 CKAD 전 영역에서 가장 자주 다루는 리소스이므로, 위 명령어들이 손에 완전히 익도록 반복 실습하세요. 특히 `set image`, `rollout status`, `rollout undo`, `scale` 네 가지는 거의 매 문제마다 쓰입니다. 함정 포인트 10가지는 시험 직전에 다시 한 번 훑어보면 실수를 크게 줄일 수 있습니다.
