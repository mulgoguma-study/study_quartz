
CKAD에서 Pod Design은 약 20%로 가장 비중이 큰 영역입니다. Deployment, Job/CronJob, Labels/Selectors, Annotations이 핵심이고, 출제 빈도도 매우 높습니다. 명령어로 빠르게 생성하는 습관이 점수와 직결됩니다.

## 시작 세팅

```bash
alias k=kubectl
export do="--dry-run=client -o yaml"
export now="--grace-period=0 --force"

# vi 사용자라면 (YAML 들여쓰기 자동)
cat >> ~/.vimrc << EOF
set tabstop=2
set expandtab
set shiftwidth=2
EOF
```

이 세팅은 시험 시작하자마자 첫 번째 터미널에서 입력하세요. Pod Design은 YAML 생성이 많아서 `$do` alias가 가장 활약하는 영역입니다.

## 자주 쓰는 YAML 생성 명령

### Pod

```bash
# 기본 Pod 생성
k run nginx --image=nginx $do > pod.yaml

# 포트, 환경변수, 명령어 포함
k run nginx --image=nginx --port=80 $do > pod.yaml
k run nginx --image=nginx --env="ENV=prod" $do > pod.yaml
k run nginx --image=nginx --command -- sleep 3600 $do > pod.yaml

# 라벨 포함
k run nginx --image=nginx --labels="app=web,tier=front" $do > pod.yaml

# 즉시 실행 (테스트용)
k run tmp --image=busybox --rm -it --restart=Never -- sh
```

### Deployment

```bash
# 기본 Deployment
k create deploy nginx --image=nginx $do > deploy.yaml

# replica 지정
k create deploy nginx --image=nginx --replicas=3 $do > deploy.yaml

# 포트 지정
k create deploy nginx --image=nginx --port=80 $do > deploy.yaml

# 생성 후 스케일
k scale deploy nginx --replicas=5

# 이미지 업데이트 (rolling update 트리거)
k set image deploy/nginx nginx=nginx:1.25
```

### Job / CronJob

```bash
# Job
k create job my-job --image=busybox $do -- echo hello > job.yaml

# CronJob
k create cronjob my-cron --image=busybox --schedule="*/1 * * * *" $do -- echo hello > cj.yaml

# CronJob 즉시 실행 (테스트)
k create job --from=cronjob/my-cron manual-run
```

### Labels / Annotations

```bash
# 라벨 추가/수정/삭제
k label pod nginx env=prod
k label pod nginx env=dev --overwrite
k label pod nginx env-           # 끝에 dash로 삭제

# 모든 Pod에 라벨
k label pods --all tier=backend

# 어노테이션 추가/삭제
k annotate pod nginx description="web server"
k annotate pod nginx description-

# 라벨로 필터링
k get pods -l app=nginx
k get pods -l 'env in (prod,staging)'
k get pods -l env!=prod
k get pods --show-labels
k get pods -L app,env       # 라벨을 컬럼으로 표시
```

## 출제 패턴

Pod Design은 6가지 유형으로 거의 정형화되어 있습니다.

### 유형 1: Deployment 생성 + 스케일 + 이미지 업데이트 (매번 출제)

"nginx Deployment를 만들고, replica를 3으로, 이후 이미지를 1.25로 업데이트하라."

```bash
k create deploy web --image=nginx --replicas=3
k set image deploy/web nginx=nginx:1.25
k rollout status deploy/web        # 진행 상태 확인
```

### 유형 2: Rolling Update 전략 설정

"maxSurge=2, maxUnavailable=0으로 설정하라."

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2
      maxUnavailable: 0
```

값은 숫자 또는 퍼센트(`"25%"`) 둘 다 가능. 퍼센트는 **반드시 문자열로** 쓰기.

### 유형 3: Rollout 관리 (history, undo)

```bash
# 변경 이력 보기
k rollout history deploy/web
k rollout history deploy/web --revision=2   # 특정 revision 상세

# 이전 버전으로 되돌리기
k rollout undo deploy/web
k rollout undo deploy/web --to-revision=2   # 특정 revision으로

# 진행 상태 / 일시정지 / 재개
k rollout status deploy/web
k rollout pause deploy/web
k rollout resume deploy/web

# 강제 재시작 (이미지 변경 없이 Pod 재생성)
k rollout restart deploy/web
```

`set image`나 `edit`로 변경하면 revision이 자동 기록됩니다. **`--record` 플래그는 deprecated**이니 쓰지 마세요.

### 유형 4: Job 생성 (병렬/완료 횟수 지정)

"5번 완료될 때까지, 동시에 2개씩 실행되는 Job을 만들어라."

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: my-job
spec:
  completions: 5         # 총 완료 횟수
  parallelism: 2         # 동시 실행 수
  backoffLimit: 4        # 재시도 횟수 (기본 6)
  activeDeadlineSeconds: 100   # 전체 시간 제한
  template:
    spec:
      restartPolicy: Never     # Job은 Never 또는 OnFailure만 가능
      containers:
      - name: worker
        image: busybox
        command: ["echo", "hello"]
```

**함정**: Job의 Pod template은 `restartPolicy: Always`를 쓸 수 없습니다. 반드시 `Never` 또는 `OnFailure`.

### 유형 5: CronJob 생성

"매분 실행되는 CronJob을 만들어라."

```bash
k create cronjob hello --image=busybox --schedule="*/1 * * * *" -- echo hello
```

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello
spec:
  schedule: "*/1 * * * *"
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  concurrencyPolicy: Allow      # Allow / Forbid / Replace
  startingDeadlineSeconds: 100
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: hello
            image: busybox
            command: ["echo", "hello"]
```

Cron 형식: `분 시 일 월 요일`. 빠르게 외울 패턴:

- `*/5 * * * *` 5분마다
- `0 * * * *` 매시 정각
- `0 0 * * *` 매일 자정
- `0 0 * * 0` 매주 일요일 자정

### 유형 6: Label / Selector / Annotation 조작

"app=web 라벨을 가진 Pod만 조회하라" 또는 "특정 Pod에 annotation을 추가하라."

```bash
# 라벨 기반 조회
k get pods -l app=web
k get pods -l 'tier in (front,back)'
k get pods -l app=web,env=prod      # 콤마는 AND

# 라벨 기반 삭제
k delete pods -l app=web

# 셀렉터로 노드 지정 (nodeSelector)
k label node worker-1 disk=ssd
```

## 함정 포인트

### 함정 1 — Job restartPolicy

```yaml
# 잘못된 예
spec:
  template:
    spec:
      restartPolicy: Always   # ❌ Job/CronJob에서 사용 불가
```

`Always`는 Deployment/Pod의 기본값이지만, Job 계열은 반드시 `Never` 또는 `OnFailure`.

### 함정 2 — CronJob의 schedule 따옴표

```yaml
schedule: */1 * * * *      # ❌ YAML 파서 에러 가능
schedule: "*/1 * * * *"    # ✅ 반드시 큰따옴표
```

별표(`*`)가 들어가면 큰따옴표로 감싸기.

### 함정 3 — Deployment selector와 template label 일치

```yaml
spec:
  selector:
    matchLabels:
      app: web         # 이거와
  template:
    metadata:
      labels:
        app: web       # 이것이 반드시 일치
```

`kubectl create deploy`로 만들면 자동으로 맞춰지지만, 직접 YAML 작성 시 자주 틀립니다. selector와 template label이 다르면 Deployment 생성 자체가 실패.

### 함정 4 — `--record` deprecated

```bash
k set image deploy/web nginx=nginx:1.25 --record   # ❌ deprecated
```

대신 `kubectl.kubernetes.io/change-cause` annotation을 직접 달아도 되지만, 시험에서는 그냥 `set image`만 쓰면 됩니다. 변경 이력은 자동 기록됨.

### 함정 5 — maxSurge / maxUnavailable 타입

```yaml
rollingUpdate:
  maxSurge: 1          # 숫자
  maxUnavailable: "25%"   # 퍼센트는 문자열
```

둘 다 동시에 0이면 업데이트가 진행 안 되므로, 문제에서 `maxUnavailable: 0`을 요구하면 `maxSurge`는 1 이상 설정.

### 함정 6 — Label selector 문법

```bash
k get pods -l 'env in (prod, staging)'      # ✅
k get pods -l 'env notin (dev)'             # ✅
k get pods -l '!env'                        # env 라벨이 없는 것
k get pods -l 'env'                         # env 라벨이 있는 것 (값 무관)
```

`in`, `notin`, `!` 문법은 따옴표로 감싸야 shell에서 해석 안 됨.

### 함정 7 — Deployment 삭제 vs Pod 삭제

```bash
k delete pod nginx-xxx       # Pod만 삭제, Deployment가 즉시 새로 생성
k delete deploy nginx        # 진짜 삭제
```

Deployment가 관리하는 Pod은 직접 삭제해도 되살아납니다. 진짜 지우려면 상위 리소스 삭제.

### 함정 8 — CronJob concurrencyPolicy

- `Allow` (기본): 이전 Job이 안 끝나도 새 Job 시작
- `Forbid`: 이전 Job이 진행 중이면 새 Job 스킵
- `Replace`: 이전 Job을 죽이고 새 Job 시작

장시간 실행되는 Job은 `Forbid` 또는 `Replace`로 명시하는 문제가 가끔 나옵니다.

## 빠르게 작성하는 팁

- **Deployment, Job, CronJob은 imperative 명령으로 거의 다 가능**합니다. YAML을 손으로 쓰지 말고 `$do`로 생성한 뒤 수정만 하세요.
- `kubectl edit` 도 적극 활용: 이미 만든 리소스를 빠르게 수정 가능.
    
    ```bash
    k edit deploy nginx     # 에디터 열림, 저장하면 즉시 적용
    ```
    
- 단, `kubectl edit`로 수정 가능한 필드는 제한적입니다. selector나 일부 immutable 필드는 못 바꿈. 그땐 삭제 후 재생성.
- 라벨/어노테이션은 거의 항상 `kubectl label` / `kubectl annotate` 명령으로 처리. YAML 수정보다 빠름.
- `--show-labels`, `-L <label>`, `-l <selector>` 조합으로 라벨 관련 문제는 cli만으로 해결.
- Rolling update 문제는 항상 `rollout status`로 완료 확인하는 습관. 미완료 상태로 다음 문제로 넘어가면 채점 시 감점 위험.
- CronJob을 즉시 테스트하려면 `kubectl create job --from=cronjob/<name>`으로 수동 Job 생성. schedule 기다리지 말 것.

## 자주 헷갈리는 차이 정리

|항목|Pod|Deployment|Job|CronJob|
|---|---|---|---|---|
|생성 명령|`k run`|`k create deploy`|`k create job`|`k create cronjob`|
|restartPolicy|Always(기본)|Always|Never/OnFailure|Never/OnFailure|
|용도|단일 실행|장기 실행 서비스|1회성 작업|주기적 작업|
|스케일링|불가|`k scale`|`parallelism`|자동 (schedule)|
|롤백|불가|`k rollout undo`|불가|불가|

---

Pod Design은 **명령어 숙련도가 곧 점수**입니다. 위 명령들을 손에 익을 때까지 반복 실습하고, 함정 포인트 8가지는 시험 직전에 다시 한 번 훑어보세요. 특히 Job/CronJob의 `restartPolicy`, Deployment의 `selector/template label 일치`, Rolling update의 `maxSurge/maxUnavailable` 타입은 가장 자주 실수하는 부분입니다.
