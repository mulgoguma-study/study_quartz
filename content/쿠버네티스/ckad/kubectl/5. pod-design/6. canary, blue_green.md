
## 카나리 배포 (Canary)

### 개념

트래픽 일부(예: 10%)만 새 버전으로 보내 검증 후 점진적으로 확대하는 전략.

```
트래픽
 ├── 90% ──▶ [v1 Deployment]  replicas: 9  (stable)
 └── 10% ──▶ [v2 Deployment]  replicas: 1  (canary)
              ↑
       같은 Service selector로 묶임 (app: myapp)
```

### 핵심 구현

```yaml
# Service - version 구분 없이 공통 label만
selector:
  app: myapp

# 비율 = replica 수로 조절
v1 replicas: 9
v2 replicas: 1
```

### 전환 명령어

```bash
# 점진 확대
kubectl scale deploy myapp-v2 --replicas=5
kubectl scale deploy myapp-v1 --replicas=5

# 완전 전환
kubectl scale deploy myapp-v1 --replicas=0
```

### 언제 쓰나

- 트래픽 많고 실사용자로 검증하고 싶을 때
- DB 스키마 변경 없는 API 서버
- 점진적 검증이 중요할 때

### 주의사항

- v1/v2 동시 처리 → 하위 호환 필수
- 순수 K8s만으론 정확한 % 제어 어려움 (실무에선 Argo Rollouts 사용)

## 블루/그린 배포 (Blue/Green)

### 개념

두 환경을 동시에 운영하다가 Service selector만 바꿔 한 번에 전환하는 전략.

```
[Blue - v1]  ✅ 운영 중       [Green - v2]  🟡 대기 중
replicas: 3                    replicas: 3

Service selector: version=blue  →  version=green 으로 전환
```

### 핵심 구현

```yaml
# Blue Deployment
selector:
  matchLabels:
    version: blue

# Green Deployment
selector:
  matchLabels:
    version: green

# Service
selector:
  app: myapp
  version: blue   # 여기만 바꾸면 전환
```

### 전환 명령어 (CKAD 핵심)

```bash
# 전환
kubectl patch svc myapp \
  -p '{"spec":{"selector":{"version":"green"}}}'

# 롤백
kubectl patch svc myapp \
  -p '{"spec":{"selector":{"version":"blue"}}}'
```

### 언제 쓰나

- DB 마이그레이션 포함 (버전 혼재가 위험할 때)
- 즉각 롤백이 반드시 필요한 경우 (금융, 결제)
- QA팀 별도 검증 환경이 필요할 때

### 주의사항

- 리소스 2배 필요
- 전환 순간 진행 중인 요청 끊길 수 있음

## 한눈에 비교

|항목|카나리|블루/그린|
|---|---|---|
|전환 방식|점진적 (replica 비율)|즉각 (selector 전환)|
|롤백 속도|점진적|즉각|
|리소스|적게 사용|2배 필요|
|버전 혼재|있음 (하위 호환 필수)|없음|
|CKAD 구현|Deployment 2개 + replica 조절|Deployment 2개 + patch selector|
|실무 툴|Argo Rollouts, Flagger|순수 K8s로 충분|

## Go 백엔드 팁

카나리 쓸 때 메트릭에 `version` 레이블 필수.

```go
prometheus.NewCounterVec(
    prometheus.CounterOpts{Name: "http_requests_total"},
    []string{"version", "status_code", "path"},
)
```

version 태그 없으면 v1/v2 에러율 분리 비교 불가.
