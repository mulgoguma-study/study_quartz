```bash
alias k=kubectl
export do="--dry-run=client -o yaml"
```

```bash
# PVC만 imperative로 가능 (PV는 YAML 직접 작성)
```

대부분 YAML을 직접 써야 하므로 **템플릿을 손에 익히는 게 핵심**입니다.

### 외워둘 PV/PVC 템플릿

**PV 템플릿** (hostPath 기반, 시험에 가장 자주 나옴):

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-001
spec:
  capacity:
    storage: 1Gi
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/data
```

**PVC 템플릿**:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-001
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 500Mi
  storageClassName: manual
```

**Pod에서 PVC 사용**:


```yaml
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: data
      mountPath: /usr/share/nginx/html
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: pvc-001
```

### PV-PVC 바인딩 조건 (절대 외울 것)

PVC가 PV에 바인딩되려면 **세 가지 모두 일치**해야 합니다.

1. `storageClassName` 일치
2. `accessModes` 일치 (PV가 PVC가 요구하는 모드를 포함)
3. PV의 `capacity` ≥ PVC의 `requests.storage`

이 중 하나라도 안 맞으면 PVC가 `Pending` 상태로 남습니다. 디버깅 시 `kubectl describe pvc`로 확인.

### AccessMode (반드시 외우기)

|약자|풀네임|의미|
|---|---|---|
|RWO|ReadWriteOnce|단일 노드에서 읽기/쓰기|
|ROX|ReadOnlyMany|여러 노드에서 읽기만|
|RWX|ReadWriteMany|여러 노드에서 읽기/쓰기|
|RWOP|ReadWriteOncePod|단일 Pod만|

### Reclaim Policy

- `Retain`: PVC 삭제해도 PV는 남음. 수동 회수
- `Delete`: PVC 삭제 시 PV도 자동 삭제
- `Recycle`: deprecated, 안 나옴

### 출제 패턴

**유형 1: PV + PVC + Pod 한 세트** (거의 매번 출제) "PV를 만들고, PVC를 만들고, Pod이 그 PVC를 마운트하게 하라."

- accessMode, storageClassName, size를 문제 지시대로 정확히 맞춰야 바인딩됨.
- 작성 후 `k get pv,pvc`로 `STATUS: Bound` 확인.

**유형 2: emptyDir 또는 hostPath 단일 문제** "두 컨테이너가 같은 volume을 공유하게 하라" 같은 식.


```yaml
spec:
  containers:
  - name: writer
    image: busybox
    command: ["sh", "-c", "echo hello > /data/msg; sleep 3600"]
    volumeMounts:
    - name: shared
      mountPath: /data
  - name: reader
    image: busybox
    command: ["sh", "-c", "cat /data/msg; sleep 3600"]
    volumeMounts:
    - name: shared
      mountPath: /data
  volumes:
  - name: shared
    emptyDir: {}
```

**유형 3: StorageClass + 동적 프로비저닝** (가끔 출제) `WaitForFirstConsumer` 모드를 요구하는 문제가 가끔 나옵니다.

### 함정 포인트

**함정 1 — storageClassName 불일치** PV에 `storageClassName: manual`로 했는데 PVC에 적지 않으면 default StorageClass를 찾아서 바인딩 실패. 양쪽 모두 명시.

**함정 2 — 빈 storageClassName** `storageClassName: ""` (빈 문자열)은 "StorageClass 없음"을 의미하는 별도 값. 생략과 다릅니다.

**함정 3 — accessMode 불일치** PVC가 RWX 요청했는데 PV가 RWO만 지원하면 바인딩 실패. 문제에서 요구하는 모드를 정확히 적기.

**함정 4 — size 비교 방향** PV capacity ≥ PVC requests. PV가 더 크거나 같아야 함. 반대로 잘못 적는 실수 흔합니다.

### 디버깅 명령 (PVC가 Pending일 때)

```bash
k get pv,pvc
k describe pvc pvc-001       # Events 확인
k describe pv pv-001
k get events --sort-by=.metadata.creationTimestamp
```

### 빠르게 작성하는 팁

- PV, PVC는 imperative 명령이 없으니 **템플릿을 외워서 즉시 작성**.
- Pod의 `volumes`와 `volumeMounts`는 항상 한 쌍으로 같이 추가. 이름 일치 필수.
- 작성 후 항상 `k get pv,pvc`로 `Bound` 확인하는 습관.
- mountPath는 컨테이너 내부 경로, hostPath는 노드 경로. 헷갈리지 않기.
