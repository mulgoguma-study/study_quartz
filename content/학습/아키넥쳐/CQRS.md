**CQRS (Command Query Responsibility Segregation, 명령 조회 책임 분리)** 패턴

조금 더 넓은 의미나 구현 방식에 따라 아래의 용어들도 함께 쓰이니, 면접 때 맥락에 맞게 꺼내 쓰시면 아주 좋습니다.

---

### 1. CQRS (명령 조회 책임 분리)

가장 정확한 아키텍처 명칭입니다.

- **개념:** 시스템에서 데이터의 **'변경(CUD/명령)'** 작업과 **'조회(R/쿼리)'** 작업의 주체를 분리하는 아키텍처 패턴입니다.
    
- **적용:** 쓰기(Command)는 무결성과 트랜잭션이 중요한 **RDB**에 철저하게 쌓고, 대용량 통계나 복잡한 조회(Query)는 읽기 성능이 압도적이고 스케일 아웃이 쉬운 **NoSQL**이나 캐시, 인덱서(Elasticsearch 등)를 바라보게 만드는 구조입니다. 시니어 면접에서 "조회 성능 최적화를 위해 CQRS 패턴을 적용했다"라고 표현하면 가장 깔끔합니다.
    

### 2. 폴리글랏 퍼시스턴스 (Polyglot Persistence)

조금 더 데이터 저장소(Storage)의 관점에 초점을 맞춘 용어입니다.

- **개념:** 하나의 서비스에서 한 종류의 DB만 고집하는 게 아니라, **데이터의 특성에 맞는 다양한 DB(RDB, NoSQL, Cache, Graph DB 등)를 혼합해서 사용하는 형태**를 말합니다.
    
- 말씀하신 "쓰기는 RDB, 통계 조행용은 NoSQL" 구조 자체가 전형적인 폴리글랏 퍼시스턴스의 예시입니다.
    

### 3. Read Replica (읽기 전용 복제본) / Materialized View (구체화된 뷰)

이를 기술적으로 구현하는 상세 기법들을 물어볼 때 나올 수 있는 키워드입니다.

- RDB에 데이터가 쌓일 때 발행되는 변경 로그(CDC, WAL 등)나 메시지 큐(Kafka, NATS 등)를 이용해 통계용 NoSQL로 데이터를 동기화하는 파이프라인을 구축하게 되는데, 이 과정에서 최종 일관성(Eventual Consistency)을 어떻게 보장했는지 시니어 면접에서 단골로 치고 들어옵니다.


통계 데이터 조회 성능을 어떻게 개선??

> _"기존 RDB에서 헤비한 통계 쿼리를 돌리면 쓰기 트랜잭션과 락(Lock) 경합이 발생해 서비스 전체에 영향을 주었습니다. 이를 해결하기 위해 **CQRS 관점**으로 접근하여, 원천 데이터는 RDB에 정교하게 쌓고, 통계성 조회 데이터는 파이프라인을 통해 **NoSQL로 비정규화(Denormalization)하여 적재**하는 방식으로 조회를 이원화했습니다."_
